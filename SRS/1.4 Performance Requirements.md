# 1.4. Performance Requirements

This section defines the expected speed, capacity, and reliability of the Simple Workforce Manager system under normal operational conditions. Performance requirements are specified quantitatively to ensure measurable system behavior for Small to Medium Enterprise (SME) deployments on local servers or private VPS infrastructure.

## 1.4.1. Response Time Requirements

The system SHALL meet the following response time targets under normal network conditions (LAN or stable internet connection with < 50ms base latency):

### 1.4.1.1. API Response Time

- **Standard CRUD Operations:** RESTful API endpoints for create, read, update, and delete operations (user management, task assignments, attendance records, reports, complaints, feedback, allowances) SHALL respond within **200 milliseconds** for 95% of requests under normal load conditions
- **Authentication Operations:** Login requests (POST /api/auth/login) including BCrypt password verification and JWT token generation SHALL complete within **500 milliseconds** for 95% of requests
- **Complex Query Operations:** Database queries involving multiple JOINs (e.g., viewing all complaints with threaded replies, attendance records with user details) SHALL return results within **500 milliseconds** for datasets up to 10,000 records
- **Search Operations:** User search functionality in chat module (ILIKE queries) SHALL return results within **300 milliseconds** for user databases up to 1,000 users

### 1.4.1.2. Real-Time Communication Latency

- **WebSocket Message Delivery:** Socket.io message transmission from sender to receiver SHALL complete within **100 milliseconds** for 95% of messages on LAN connections
- **Socket Authentication:** WebSocket connection establishment and JWT authentication SHALL complete within **200 milliseconds**
- **Presence Updates:** User online/offline status updates via Socket.io SHALL propagate to connected clients within **150 milliseconds**

### 1.4.1.3. User Interface Loading Time

- **Initial Page Load:** React application initial bundle load and rendering SHALL complete within **3 seconds** on modern browsers (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+)
- **Production Bundle Size:** React 19.2.0 application with Ant Design 5.28.0 produces the following bundle characteristics:
  - **Main Application Bundle:** **~800 KB - 1.2 MB** (minified, uncompressed)
  - **Vendor Chunks:** **~500 KB** (React 19.2.0, ReactDOM, Ant Design 5.28.0, Socket.io-client 4.8.1)
  - **Total Initial Load:** **~1.5 MB - 2 MB** before gzip compression
  - **Gzipped Transfer Size:** **~400 KB - 600 KB** (typical 3:1 compression ratio with gzip)
  - **Code Splitting:** react-scripts 5.0.1 automatically splits vendor and application code into separate chunks
  - **Lazy Loading:** NOT currently implemented; all routes and components load eagerly on initial page load
- **Dashboard Loading:** Dashboard page with aggregated data (attendance summary, task counts, recent activities) SHALL render within **2 seconds** including all API calls
- **Navigation Between Pages:** Client-side route transitions SHALL complete within **100 milliseconds** (excluding API data fetching)
- **Form Submission Feedback:** User interface SHALL provide visual feedback (loading indicators, button state changes) within **50 milliseconds** of form submission

## 1.4.2. Concurrent User Capacity

The system SHALL support the following concurrent user loads based on typical SME workforce sizes:

### 1.4.2.1. Active User Capacity

- **Concurrent Active Users:** The Node.js backend SHALL support a minimum of **50 concurrent active users** and a target of **100 concurrent active users** performing standard operations (viewing pages, submitting forms, updating records) without performance degradation exceeding 20% of baseline response times
- **Peak Load Handling:** The system SHALL handle peak loads of **150 concurrent users** for short durations (< 5 minutes) such as shift change times when multiple staff members clock in/out simultaneously
- **Database Connection Pool Configuration:** PostgreSQL connection pool uses pg library with the following default settings:
  - **Default Maximum Connections:** **10 concurrent connections** (pg library default)
  - **Idle Connection Timeout:** **10 seconds** before closing idle connections
  - **Connection Timeout:** **0 milliseconds** (no timeout, waits indefinitely for available connection)
  - **Minimum Pool Size:** **0** (connections created on demand)
- **Recommended Pool Configuration:** For 50-100 concurrent users, the following explicit configuration is recommended:
  - max: **20-50 connections** (based on concurrent user load)
  - idleTimeoutMillis: **30000** (30 seconds)
  - connectionTimeoutMillis: **2000** (2 seconds to prevent indefinite waiting)
  - min: **5** (maintain minimum 5 connections for faster response)

### 1.4.2.2. Real-Time Chat Capacity

- **Simultaneous WebSocket Connections:** The Socket.io server SHALL maintain **100 simultaneous WebSocket connections** corresponding to the maximum concurrent user capacity
- **Message Throughput:** The chat system SHALL process a minimum of **50 messages per second** across all active conversations without message delivery delays exceeding 200 milliseconds
- **Conversation Scalability:** The system SHALL support **500 active conversations** (unique user pairs) with message history retrieval completing within 500 milliseconds per conversation
- **Socket.io Configuration Details:** The system uses Socket.io 4.8.1 with the following default settings:
  - **Ping Timeout:** **20 seconds** (time to wait for ping response before considering connection dead)
  - **Ping Interval:** **25 seconds** (interval between ping packets sent to clients)
  - **Max HTTP Buffer Size:** **1 MB** (maximum size for HTTP long-polling messages)
  - **Transport Methods:** WebSocket (primary), HTTP long-polling (automatic fallback)
  - **Connection Overhead:** Approximately **2-5 KB** per connection for handshake and metadata
  - **Theoretical Maximum:** Single Node.js instance can support ~**10,000 concurrent WebSocket connections** (hardware dependent)

### 1.4.2.3. Session Management

- **Active Sessions:** The system SHALL maintain **100 concurrent authenticated sessions** with JWT token validation overhead not exceeding 10 milliseconds per request
- **Session Storage:** Browser LocalStorage SHALL persist JWT tokens with retrieval time under **5 milliseconds**

## 1.4.3. Scalability Requirements

The system SHALL demonstrate scalability characteristics suitable for SME growth:

### 1.4.3.1. Data Volume Scalability

- **Database Record Capacity:** PostgreSQL database SHALL support growth to **1 million total records** across all tables without query performance degradation exceeding 50% of baseline performance, provided proper indexing is maintained
- **Current Indexing Status:** The system currently has the following indexes automatically created:
  - **Primary Key Indexes:** Automatically created on all SERIAL PRIMARY KEY columns (user_id, task_id, attendance_id, message_id, complaint_id, feedback_id, allowance_id, conversation_id, report_id)
  - **Unique Constraint Indexes:** Automatically created on UNIQUE columns (users.username, users.email, user_profiles.phone_number, user_profiles.user_id, conversations(user1_id, user2_id), system_settings.setting_key)
  - **Foreign Key Indexes:** NOT automatically created by PostgreSQL; manual creation required for optimal performance
- **Recommended Performance Indexes:** The following indexes SHOULD be created for optimal query performance but are NOT currently implemented:
  ```sql
  -- Task queries by assignee and status
  CREATE INDEX idx_tasks_assigned_to ON tasks(assigned_to);
  CREATE INDEX idx_tasks_assigned_by ON tasks(assigned_by);
  CREATE INDEX idx_tasks_status ON tasks(status);
  CREATE INDEX idx_tasks_due_date ON tasks(due_date);
  
  -- Attendance queries by user and date
  CREATE INDEX idx_attendance_user_id ON attendance(user_id);
  CREATE INDEX idx_attendance_date ON attendance(attendance_date);
  CREATE INDEX idx_attendance_user_date ON attendance(user_id, attendance_date);
  
  -- Message queries by conversation and timestamp
  CREATE INDEX idx_messages_conversation_id ON messages(conversation_id);
  CREATE INDEX idx_messages_sent_at ON messages(sent_at);
  CREATE INDEX idx_messages_conversation_time ON messages(conversation_id, sent_at);
  
  -- Complaint and feedback queries by status and user
  CREATE INDEX idx_complaints_user_id ON complaints(user_id);
  CREATE INDEX idx_complaints_status ON complaints(status);
  CREATE INDEX idx_feedback_user_id ON feedback(user_id);
  CREATE INDEX idx_feedback_replied_by ON feedback(replied_by);
  
  -- Report and allowance queries by user
  CREATE INDEX idx_reports_user_id ON reports(user_id);
  CREATE INDEX idx_allowances_user_id ON allowances(user_id);
  ```
- **Attendance Records:** The system SHALL efficiently handle **100,000 attendance records** (approximately 2 years of daily attendance for 100 employees) with query response times under 500 milliseconds when proper indexes are created
- **Chat Message History:** The system SHALL store and retrieve **500,000 chat messages** with conversation history queries completing within 500 milliseconds when filtered by conversation_id and cleared_at timestamps with proper indexing
- **Task Management:** The system SHALL manage **10,000 active tasks** with list views and filtering operations completing within 500 milliseconds with recommended indexes in place

### 1.4.3.2. Vertical Scaling

- **CPU Utilization:** The Node.js backend SHALL efficiently utilize additional CPU cores when host machine is upgraded from dual-core to quad-core or higher configurations, with linear performance improvement for concurrent request handling
- **Memory Utilization:** The system SHALL leverage increased RAM allocation (from 8GB to 16GB or higher) to:
  - Increase PostgreSQL shared_buffers for improved query caching
  - Expand Node.js heap size for handling larger concurrent user loads
  - Support larger connection pools without memory exhaustion
- **Storage Performance:** The system SHALL benefit from SSD upgrades with database query performance improvements of 50-200% compared to HDD storage for read-heavy operations

### 1.4.3.3. Horizontal Scaling Limitations

- **Single-Server Architecture:** The current system version is designed for single-server deployment and SHALL NOT support horizontal scaling across multiple application servers or database replicas
- **Future Scalability Path:** The system architecture SHALL be documented to facilitate future migration to load-balanced multi-server deployments if organizational growth exceeds single-server capacity (> 200 concurrent users)

## 1.4.4. Availability Requirements

The system SHALL maintain high availability appropriate for business-critical workforce management:

### 1.4.4.1. Uptime Targets

- **Business Hours Availability:** The system SHALL maintain **99.9% uptime** during defined business hours (typically 8:00 AM to 6:00 PM local time, Monday through Friday), allowing for maximum **43 minutes of downtime per month** during business hours
- **24/7 Availability Target:** For organizations requiring round-the-clock access, the system SHALL target **99.5% uptime** across all hours, allowing for maximum **3.6 hours of downtime per month**
- **Planned Maintenance Windows:** Scheduled maintenance (database backups, system updates, security patches) SHALL be performed during off-peak hours with advance notification of minimum **24 hours** to system administrators

### 1.4.4.2. Fault Recovery

- **Process Management Status:** The system does NOT include Docker containerization or automated process management in the current codebase
- **Automatic Restart Requirement:** System administrators SHALL implement external process management using one of the following options:
  - **PM2 (Recommended):** `pm2 start backend/index.js --name swm-backend` with PM2 startup scripts for automatic restart on system reboot
  - **systemd:** Create systemd service unit for automatic restart on failure
  - **Docker (Optional):** Deploy with `restart: always` policy for automatic container restart
- **Restart Time Target:** With PM2 or systemd, application SHALL restart within **30 seconds** of crash detection
- **Database Recovery:** PostgreSQL SHALL recover from unexpected shutdown using Write-Ahead Logging (WAL) with automatic crash recovery completing within **60 seconds** for databases up to 10GB
- **Connection Recovery:** Socket.io clients (frontend) SHALL automatically attempt reconnection with exponential backoff strategy, achieving reconnection within **5 seconds** after server recovery
- **Session Persistence:** User sessions SHALL remain valid across server restarts provided JWT tokens have not expired (1-hour token lifetime from issuance)

### 1.4.4.3. Error Handling

- **Graceful Degradation:** In the event of database connection failures, the system SHALL display user-friendly error messages within **2 seconds** and log detailed error information for administrator review
- **Transaction Rollback:** Failed database transactions SHALL rollback completely within **100 milliseconds** to maintain data consistency
- **API Error Responses:** All API endpoints SHALL return appropriate HTTP error codes (400, 401, 403, 404, 409, 500) with descriptive error messages within **200 milliseconds** of error detection

## 1.4.5. Security Performance Requirements

The system SHALL implement security measures with acceptable performance overhead:

### 1.4.5.1. Password Hashing Performance

- **BCrypt Hashing Duration:** Password hashing using BCrypt with salt rounds = 10 (bcrypt.genSalt(10)) SHALL complete within **100-300 milliseconds** per operation, providing sufficient computational cost to deter brute-force attacks while maintaining acceptable user experience during login and password change operations
- **BCrypt Configuration:** The system uses bcrypt 6.0.0 with the following characteristics:
  - **Salt Rounds:** 10 (2^10 = 1,024 iterations)
  - **Hash Length:** 60 characters (bcrypt output format)
  - **Algorithm:** Blowfish-based adaptive hash function
- **Rate Limiting Status:** The system does NOT currently implement rate limiting middleware
- **Security Vulnerability:** Without rate limiting, the system is vulnerable to:
  - Brute-force password attacks
  - API endpoint abuse
  - Denial of Service (DoS) through excessive requests
- **Recommended Implementation:** Install and configure express-rate-limit middleware:
  ```javascript
  const rateLimit = require('express-rate-limit');
  
  // Login endpoint rate limiter
  const loginLimiter = rateLimit({
    windowMs: 15 * 60 * 1000, // 15 minutes
    max: 5, // 5 attempts per window
    message: 'Too many login attempts, please try again later',
    standardHeaders: true,
    legacyHeaders: false,
  });
  
  app.use('/api/auth/login', loginLimiter);
  
  // Global API rate limiter
  const apiLimiter = rateLimit({
    windowMs: 1 * 60 * 1000, // 1 minute
    max: 100, // 100 requests per minute per IP
  });
  
  app.use('/api/', apiLimiter);
  ```
- **Target Rate Limits:** Once implemented, the system SHOULD enforce:
  - **Login Attempts:** Maximum **5 failed attempts per username per 15-minute window**
  - **API Requests:** Maximum **100 requests per IP address per minute**
  - **Password Reset:** Maximum **3 requests per email per hour**

### 1.4.5.2. Token Validation Performance

- **JWT Verification Speed:** JWT token signature verification using HMAC SHA256 SHALL complete within **10 milliseconds** per request to minimize authentication overhead on protected API endpoints
- **Token Payload Extraction:** Decoding JWT token payload to extract user information (user_id, role) SHALL complete within **5 milliseconds**

### 1.4.5.3. Database Query Security

- **Parameterized Query Overhead:** Using parameterized queries to prevent SQL injection SHALL add negligible overhead (< **5 milliseconds**) compared to direct string concatenation
- **Connection Pool Security:** Secure database connection establishment with SSL/TLS encryption (when enabled) SHALL add maximum **50 milliseconds** overhead to initial connection time

## 1.4.6. Data Integrity and Backup Requirements

The system SHALL ensure data persistence and recoverability:

### 1.4.6.1. Transaction Performance

- **ACID Compliance:** All database operations SHALL maintain ACID (Atomicity, Consistency, Isolation, Durability) properties with transaction commit times under **100 milliseconds** for single-table operations and under **500 milliseconds** for multi-table transactions
- **Write Durability:** Critical data (attendance records, financial allowances, user credentials) SHALL be committed to PostgreSQL disk storage immediately upon transaction commit using synchronous_commit = on configuration
- **Transaction Isolation:** The system SHALL use READ COMMITTED isolation level by default, with serialization conflicts occurring in less than **0.1%** of concurrent transactions under normal load

### 1.4.6.2. Backup Performance

- **Current Backup Status:** The system does NOT include automated backup scripts or scheduling in the codebase
- **Manual Backup Procedure:** System administrators SHALL manually execute PostgreSQL backups using:
  ```bash
  # Basic backup
  pg_dump -U postgres -d simple_workforce_manager > backup_$(date +%Y%m%d).sql
  
  # Compressed backup (recommended)
  pg_dump -U postgres -d simple_workforce_manager | gzip > backup_$(date +%Y%m%d).sql.gz
  
  # Backup with custom format (faster restore)
  pg_dump -U postgres -d simple_workforce_manager -Fc > backup_$(date +%Y%m%d).dump
  ```
- **Recommended Automated Backup:** Implement cron job for daily automated backups:
  ```bash
  # Edit crontab: crontab -e
  # Add line for daily 2 AM backup with 30-day retention
  0 2 * * * pg_dump -U postgres -d simple_workforce_manager | gzip > /backups/swm_$(date +\%Y\%m\%d).sql.gz && find /backups -name "swm_*.sql.gz" -mtime +30 -delete
  ```
- **Database Dump Duration:** pg_dump operations SHALL complete within **5 minutes** for databases up to 10GB without blocking normal operations (pg_dump uses MVCC snapshots for consistent backups)
- **Backup Frequency Target:** Once automated, the system SHOULD perform:
  - **Daily Backups:** Scheduled during off-peak hours (e.g., 2:00 AM local time)
  - **Retention Policy:** Minimum **7 daily backups** and **4 weekly backups** (28 days total retention)
  - **Monthly Archives:** Optional long-term retention of monthly backups for compliance
- **Backup Storage:** Database backup files SHALL be compressed using gzip compression, achieving typical compression ratios of **5:1 to 10:1** for text-heavy data (chat messages, reports, complaints, feedback)
- **Backup File Sizes:** Expected backup sizes for typical SME deployment:
  - **Uncompressed:** ~500 MB - 2 GB (depending on data volume)
  - **Gzip Compressed:** ~50 MB - 200 MB (10:1 compression for text data)
- **Restore Time:** Database restoration from backup SHALL complete within **10 minutes** for databases up to 10GB:
  ```bash
  # Restore from gzipped backup
  gunzip < backup_20250124.sql.gz | psql -U postgres -d simple_workforce_manager
  
  # Restore from custom format
  pg_restore -U postgres -d simple_workforce_manager backup_20250124.dump
  ```
- **System Downtime:** Total system downtime during restore SHALL not exceed **15 minutes** including database restoration and application restart

### 1.4.6.3. Data Validation Performance

- **Unique Constraint Checking:** Database unique constraint validation (username, email, phone_number) SHALL complete within **50 milliseconds** using B-tree indexes
- **Foreign Key Validation:** Foreign key constraint checking SHALL add maximum **20 milliseconds** overhead per INSERT/UPDATE operation
- **ENUM Type Validation:** ENUM type constraint validation (user_role, task_status, complaint_status, sex_type, conversation_status) SHALL complete within **5 milliseconds**

## 1.4.11. Technology Version Performance Characteristics

This section documents the performance characteristics of the specific technology versions used in the Simple Workforce Manager system.

### 1.4.11.1. Node.js Performance Characteristics

- **Version:** Node.js 18.0.0 or higher (LTS - Long Term Support)
- **JavaScript Engine:** V8 engine with Just-In-Time (JIT) compilation for optimized JavaScript execution
- **Event Loop Architecture:** Single-threaded event loop with libuv for asynchronous I/O operations
- **Concurrency Model:** Non-blocking I/O enables handling thousands of concurrent connections on single thread
- **Memory Management:**
  - Default heap size: ~1.4 GB (32-bit systems) or ~1.7 GB (64-bit systems)
  - Configurable via --max-old-space-size flag (e.g., node --max-old-space-size=4096 index.js for 4GB)
  - Garbage collection: Generational garbage collector with incremental marking
- **Performance Characteristics:**
  - Event loop tick: < 1ms under normal load
  - Async operation overhead: ~0.1-1ms per operation
  - Module loading: ~10-50ms for initial require() calls (cached thereafter)
- **Recommended Configuration:**
  ```bash
  # Production startup with increased heap size
  node --max-old-space-size=2048 index.js
  ```

### 1.4.11.2. PostgreSQL Performance Characteristics

- **Version:** PostgreSQL 13.0 or higher
- **Query Execution:** Cost-based query optimizer with EXPLAIN ANALYZE for query planning
- **Default Configuration Values:**
  - shared_buffers: 128 MB (recommended: 25% of system RAM)
  - effective_cache_size: 4 GB (recommended: 50-75% of system RAM)
  - work_mem: 4 MB (per operation; increase for complex queries)
  - maintenance_work_mem: 64 MB (for VACUUM, CREATE INDEX)
  - max_connections: 100 (default; adjust based on connection pool size)
- **Connection Overhead:**
  - New connection establishment: ~1-2 ms
  - Connection via pool (reused): < 0.1 ms
  - SSL connection overhead: +0.5-1 ms
- **Query Performance:**
  - Simple SELECT by primary key: < 1 ms
  - JOIN queries (2-3 tables): 5-50 ms (depends on indexes and data volume)
  - Full table scan (10,000 rows): 50-200 ms
  - Index scan: 1-10 ms per 1,000 rows
- **Transaction Overhead:**
  - BEGIN/COMMIT: ~0.5-1 ms
  - ROLLBACK: ~0.1-0.5 ms
- **Recommended Tuning:**
  ```sql
  -- For 8GB RAM system
  ALTER SYSTEM SET shared_buffers = '2GB';
  ALTER SYSTEM SET effective_cache_size = '6GB';
  ALTER SYSTEM SET work_mem = '16MB';
  ALTER SYSTEM SET maintenance_work_mem = '512MB';
  SELECT pg_reload_conf();
  ```

### 1.4.11.3. React Performance Characteristics

- **Version:** React 19.2.0
- **Rendering Engine:** Concurrent rendering with automatic batching of state updates
- **Virtual DOM:** Efficient diffing algorithm for minimal DOM manipulations
- **Performance Features:**
  - Automatic batching: Multiple setState calls batched into single render
  - Concurrent features: Time-slicing for responsive UI during heavy computations
  - Suspense: Declarative loading states for async operations
- **Bundle Size Impact:**
  - React core: ~6 KB (gzipped)
  - ReactDOM: ~130 KB (gzipped)
  - Ant Design 5.28.0: ~500 KB (uncompressed), ~150 KB (gzipped)
  - Total vendor bundle: ~400-600 KB (gzipped)
- **Rendering Performance:**
  - Initial mount: 10-50 ms (depends on component complexity)
  - Re-render: 1-10 ms (with proper optimization)
  - Virtual DOM diff: < 1 ms for typical component trees
- **Optimization Techniques:**
  - React.memo() for preventing unnecessary re-renders
  - useMemo() and useCallback() for expensive computations
  - Code splitting with React.lazy() and Suspense (not currently implemented)
  - Virtualization for long lists (react-window, react-virtualized)

### 1.4.11.4. Socket.io Performance Characteristics

- **Version:** Socket.io 4.8.1 (server and client)
- **Transport Protocol:** WebSocket (primary) with Engine.IO fallback to HTTP long-polling
- **Connection Overhead:**
  - WebSocket handshake: ~50-100 ms (includes HTTP upgrade)
  - Per-connection memory: ~2-5 KB
  - Ping/pong overhead: ~100 bytes per 25-second interval
- **Message Performance:**
  - Message serialization: < 1 ms (JSON.stringify)
  - Message transmission: Network latency + ~1-5 ms processing
  - Message deserialization: < 1 ms (JSON.parse)
- **Scalability:**
  - Single Node.js instance: ~10,000 concurrent connections (theoretical maximum)
  - Practical limit: ~1,000-5,000 connections (depends on message frequency and hardware)
  - Memory per 1,000 connections: ~50-100 MB
- **Configuration Options:**
  - pingTimeout: 20 seconds (default)
  - pingInterval: 25 seconds (default)
  - maxHttpBufferSize: 1 MB (default)
  - transports: ['websocket', 'polling'] (default order)
- **Performance Considerations:**
  - Broadcasting to N clients: O(N) operation, ~0.1-1 ms per client
  - Room-based messaging: Efficient filtering, minimal overhead
  - Acknowledgment callbacks: +1 round-trip time (RTT) latency

### 1.4.11.5. Express.js Performance Characteristics

- **Version:** Express 5.1.0

  - Per middleware: ~0.01-0.1 ms
  - JSON body parsing: ~1-5 ms (depends on payload size)
  - CORS middleware: < 0.1 ms
  - JWT verification: ~5-10 ms (includes crypto operations)
- **Routing Performance:**
  - Route matching: < 0.1 ms (uses fast path-to-regexp)

- **Request/Response Cycle:**
  - Minimum overhead: ~1-2 ms (empty route handler)

### 1.4.11.7. Performance Optimization Recommendations

Based on the technology stack, the following optimizations are recommended:

1. **Database Connection Pooling:** Configure explicit pool size (20-50 connections)
2. **Database Indexing:** Create recommended indexes for foreign keys and frequently queried fields
3. **React Code Splitting:** Implement React.lazy() for route-based code splitting
4. **Compression Middleware:** Add compression middleware for gzip response compression
5. **Static Asset Caching:** Configure cache headers for static assets (1 year for versioned files)
6. **CDN for Static Assets:** Serve React build files from CDN for faster global delivery
7. **PostgreSQL Query Optimization:** Use EXPLAIN ANALYZE for slow queries and add appropriate indexes
8. **Rate Limiting:** Implement express-rate-limit to prevent API abuse
9. **HTTP/2 Support:** Use reverse proxy (nginx, Apache) with HTTP/2 for multiplexing
10. **Monitoring:** Implement morgan for HTTP logging and custom metrics collection
