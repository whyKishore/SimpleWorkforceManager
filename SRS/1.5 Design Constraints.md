# 1.5. Design Constraints

This section outlines the limitations and restrictions imposed on the Simple Workforce Manager system by hardware capabilities, software environment dependencies, architectural decisions, and business requirements. These constraints define the boundaries within which the system must operate and establish non-negotiable requirements that SHALL be adhered to throughout the system lifecycle.

## 1.5.1. Platform and Technology Constraints

### 1.5.1.1. Technology Stack Restrictions

- **PERN Stack Mandate:** The system MUST be built exclusively using the PERN technology stack consisting of:
  - **PostgreSQL 13.0 or higher:** Relational database management system for all data persistence
  - **Express.js 5.1.0 or higher:** Web application framework for backend API implementation
  - **React 19.2.0 or higher:** Frontend user interface library for client-side rendering
  - **Node.js 18.0.0 or higher:** JavaScript runtime environment for backend execution
- **No Alternative Technologies:** The system SHALL NOT incorporate alternative database systems (MySQL, MongoDB, etc.), backend frameworks (Django, Spring Boot, etc.), or frontend frameworks (Angular, Vue.js, etc.) in the core application architecture
- **JavaScript Only:** All application code MUST be written in JavaScript (ES6+); TypeScript is NOT used in the current implementation
- **No TypeScript:** The codebase does NOT include TypeScript files (.ts, .tsx) or TypeScript configuration; all code is plain JavaScript
- **CommonJS Module System:** The backend MUST use CommonJS module system (require/module.exports); ES6 modules (import/export) are NOT used in the backend
- **ES6 Modules in Frontend:** The frontend uses ES6 module syntax (import/export) via React build tooling (react-scripts)

### 1.5.1.2. Runtime Environment Constraints

- **Node.js Single-Threaded Event Loop:** The backend MUST operate within the constraints of Node.js's single-threaded event loop architecture:
  - CPU-intensive operations (complex report generation, data aggregation, bulk processing) MUST be optimized to avoid blocking the main event loop
  - Long-running synchronous operations (> 100ms) MUST be refactored into asynchronous operations or offloaded to worker threads
  - Blocking operations SHALL NOT be performed on the main thread during request handling
- **Asynchronous I/O Requirement:** All database queries, file system operations, and network requests MUST use asynchronous patterns (Promises, async/await) to maintain system responsiveness
- **Memory Constraints:** The Node.js process MUST operate within default heap size limits (~1.7GB on 64-bit systems) unless explicitly configured otherwise; memory-intensive operations MUST implement streaming or pagination to prevent heap exhaustion

### 1.5.1.3. Deployment Constraints

- **No Docker Configuration:** The system does NOT include Docker containerization files (Dockerfile, docker-compose.yml) in the current codebase
- **Manual Deployment Required:** The system MUST be deployed manually by:
  - Installing Node.js runtime on host system
  - Installing PostgreSQL database server
  - Cloning or copying application files
  - Installing npm dependencies (npm install)
  - Configuring environment variables (.env files)
  - Running database initialization scripts
  - Starting backend and frontend processes separately
- **Optional Docker Support:** Organizations MAY create their own Docker configurations for containerized deployment, but this is NOT provided by default
- **Process Management Requirement:** Production deployments REQUIRE external process management:
  - **PM2 (Recommended):** For automatic restart and process monitoring
  - **systemd:** For Linux system service integration
  - **Windows Service:** For Windows Server deployments
  - **Docker (Optional):** If organization creates custom Docker configuration
- **Host Operating System Compatibility:** The system MUST be deployable on the following host operating systems:
  - Linux distributions: Ubuntu 20.04+, Debian 11+, CentOS 8+, RHEL 8+
  - Windows: Windows Server 2019+, Windows 10/11 Professional
  - macOS: macOS 11+ (for development and small-scale deployments)
- **No Cloud-Specific Dependencies:** The system SHALL NOT depend on cloud-specific services (AWS Lambda, Azure Functions, Google Cloud Platform services) that would prevent on-premise deployment

### 1.5.1.4. Database Constraints

- **PostgreSQL Exclusivity:** All structured data MUST be stored in PostgreSQL relational database; no alternative data stores (NoSQL databases, in-memory caches, file-based storage) SHALL be used for primary data persistence
- **No ORM or Query Builder:** The system uses raw SQL queries via pg library; no Object-Relational Mapping (ORM) tools (Sequelize, TypeORM, Prisma) or query builders (Knex.js) are used
- **Parameterized Queries Only:** All database queries MUST use parameterized statements (db.query(text, params)) to prevent SQL injection; string concatenation for query construction is STRICTLY FORBIDDEN
- **SQL Compliance:** All database operations MUST use standard SQL syntax compatible with PostgreSQL 13.0+; vendor-specific extensions MUST be avoided to maintain upgrade compatibility
- **No Schema Migration Framework:** The system does NOT use formal database migration frameworks (Flyway, Liquibase, Knex migrations):
  - Initial schema creation via setupDatabase.js script
  - Schema updates MUST be performed manually via SQL scripts
  - No automated migration versioning or rollback capability
- **Schema Idempotency:** setupDatabase.js uses CREATE TYPE IF NOT EXISTS and CREATE TABLE IF NOT EXISTS for idempotent schema creation
- **ACID Compliance:** All critical transactions (financial records, attendance logs, user authentication) MUST maintain ACID properties (Atomicity, Consistency, Isolation, Durability)
- **No Caching Layer:** The system does NOT implement database query caching (Redis, Memcached); all queries execute against PostgreSQL directly

### 1.5.1.5. Frontend Constraints

- **React Component Architecture:** The user interface MUST be implemented using React functional components with Hooks; class-based components are DEPRECATED
- **Ant Design UI Framework:** All user interface components MUST utilize Ant Design 5.28.0 component library for consistency; custom UI components SHALL only be created when Ant Design components are insufficient
- **Single Page Application (SPA):** The frontend MUST be implemented as a Single Page Application with client-side routing via React Router DOM 7.9.5; traditional multi-page server-rendered architecture is PROHIBITED
- **Browser Compatibility:** The frontend MUST support the following minimum browser versions:
  - Google Chrome 90+
  - Mozilla Firefox 88+
  - Apple Safari 14+
  - Microsoft Edge 90+
  - Mobile browsers: iOS Safari 14+, Chrome Mobile 90+

## 1.5.2. Performance Constraints

### 1.5.2.1. Hardware Resource Constraints

- **Minimum Hardware Requirements:** The system MUST operate on hardware meeting the following minimum specifications:
  - **CPU:** Dual-core processor at 2.0 GHz or higher
  - **RAM:** 4 GB minimum (8 GB recommended for optimal performance)
  - **Storage:** 20 GB available disk space (SSD strongly recommended)
  - **Network:** Gigabit Ethernet adapter or equivalent Wi-Fi connectivity
- **Performance Degradation Acceptance:** The system MUST maintain acceptable performance (response times within 150% of baseline) on minimum hardware specifications under normal load (50 concurrent users)
- **Resource Efficiency Mandate:** The application MUST be optimized for resource efficiency to minimize hardware requirements for SME deployments:
  - Idle CPU utilization MUST remain below 10%
  - Memory footprint MUST not exceed 2 GB under zero load
  - Database storage growth MUST be predictable and manageable (< 100 MB per month for typical usage)

### 1.5.2.2. Network Latency Constraints

- **LAN Latency Requirement:** For real-time features (WebSocket chat, live attendance updates) to function correctly, network latency between client and server MUST remain below **100 milliseconds**
- **WebSocket Dependency:** Real-time communication features MUST use WebSocket protocol (via Socket.io 4.8.1); network infrastructure MUST support WebSocket connections without blocking or downgrading to long-polling
- **Network Bandwidth Constraint:** The system MUST operate effectively on network connections providing minimum **1 Mbps per concurrent user**; bandwidth-intensive operations (large file transfers, video streaming) are NOT supported
- **Offline Operation Limitation:** The system SHALL NOT support offline operation; continuous network connectivity between client and server is REQUIRED for all functionality

### 1.5.2.3. Scalability Constraints

- **Single-Server Architecture:** The current system design is CONSTRAINED to single-server deployment; horizontal scaling across multiple application servers is NOT supported
- **Concurrent User Limit:** The system is DESIGNED for **50-100 concurrent active users**; deployments exceeding 200 concurrent users MUST consider hardware upgrades or architectural modifications
- **Database Size Constraint:** Optimal performance is GUARANTEED for databases up to **10 GB**; larger databases MAY require additional indexing, query optimization, or hardware upgrades
- **Vertical Scaling Only:** Performance improvements MUST be achieved through vertical scaling (increasing CPU, RAM, storage on single server) rather than horizontal scaling (adding multiple servers)

### 1.5.2.4. Response Time Constraints

- **API Response Time Mandate:** All RESTful API endpoints MUST respond within **500 milliseconds** for 95% of requests under normal load conditions; endpoints consistently exceeding this threshold MUST be optimized
- **Database Query Constraint:** Individual database queries MUST complete within **500 milliseconds**; queries exceeding this threshold MUST be optimized through indexing, query rewriting, or result pagination
- **Real-Time Message Latency:** WebSocket message delivery MUST complete within **100 milliseconds** on LAN connections; higher latencies indicate network infrastructure issues requiring resolution

## 1.5.3. Security and Privacy Constraints

### 1.5.3.1. Data Storage Security Constraints

- **Password Hashing Mandate:** All user passwords MUST be hashed using BCrypt algorithm with minimum **10 salt rounds** before database storage; plain text password storage is STRICTLY PROHIBITED
- **No Reversible Encryption:** Password hashing MUST use one-way cryptographic hash functions; reversible encryption of passwords is FORBIDDEN
- **Sensitive Data Protection:** Personally Identifiable Information (PII) including email addresses, phone numbers, and employment details MUST be stored with appropriate database-level access controls
- **Database Encryption:** For high-security deployments, PostgreSQL MUST be configured with encryption at rest; unencrypted database files on production servers are DISCOURAGED

### 1.5.3.2. Authentication and Authorization Constraints

- **Stateless JWT Requirement:** User authentication MUST rely exclusively on stateless JSON Web Tokens (JWT) with the following constraints:
  - Token expiration MUST be set to **1 hour** from issuance
  - Tokens MUST be signed using HMAC SHA256 algorithm with secure secret key
  - Token payload MUST contain only non-sensitive user identification (user_id, role)
  - Tokens MUST be transmitted via HTTP Authorization header with Bearer scheme
- **No Server-Side Session Storage:** The system SHALL NOT maintain server-side session storage (Redis, in-memory sessions); all session state MUST be contained within JWT tokens
- **Role-Based Access Control (RBAC) Enforcement:** Authorization MUST be enforced at the middleware level for every protected API route:
  - All routes MUST verify JWT token validity before processing requests
  - Role-based permissions (admin, manager, staff) MUST be checked via middleware before route handler execution
  - Unauthorized access attempts MUST return HTTP 401 (Unauthorized) or 403 (Forbidden) status codes
- **No Client-Side Authorization:** Authorization decisions SHALL NOT be made on the client side; all access control MUST be enforced by backend middleware

### 1.5.3.3. Communication Security Constraints

- **HTTPS Requirement for Production:** Production deployments MUST use HTTPS protocol with valid SSL/TLS certificates; HTTP-only deployments are ACCEPTABLE only for development and internal LAN environments
- **WebSocket Security:** Socket.io connections MUST authenticate using JWT tokens; unauthenticated WebSocket connections SHALL be immediately disconnected
- **CORS Configuration:** Cross-Origin Resource Sharing (CORS) MUST be explicitly configured to allow only trusted frontend origins; wildcard CORS policies are PROHIBITED in production

### 1.5.3.4. Input Validation Constraints

- **Server-Side Validation Mandate:** All user inputs MUST be validated on the server side before processing; client-side validation alone is INSUFFICIENT
- **SQL Injection Prevention:** All database queries MUST use parameterized statements; string concatenation for SQL query construction is STRICTLY FORBIDDEN
- **XSS Prevention:** React's automatic escaping MUST be relied upon for XSS prevention; dangerouslySetInnerHTML usage is PROHIBITED unless absolutely necessary with explicit sanitization

## 1.5.4. Usability Constraints

### 1.5.4.1. Responsive Design Constraints

- **Mobile Web Browser Support:** The staff interface (attendance clock-in/out, chat, task viewing) MUST be fully functional and usable on mobile web browsers:
  - Touch-optimized controls with minimum **44x44 pixel** touch targets
  - Responsive layout adapting to screen sizes from **375px** (mobile) to **1920px** (desktop)
  - No horizontal scrolling required on mobile devices
- **No Native Mobile Applications:** The system SHALL NOT provide native iOS or Android applications; all mobile access MUST occur through mobile web browsers
- **Desktop-First Design:** Administrative interfaces (user management, system settings, reports) MAY be optimized for desktop usage; mobile optimization for admin features is OPTIONAL

### 1.5.4.2. User Interface Constraints

- **Ant Design Component Library:** All UI components MUST utilize Ant Design 5.28.0 design system for visual consistency:
  - Standard Ant Design color schemes, typography, and spacing MUST be maintained
  - Custom styling MUST follow Ant Design theming guidelines
  - Component behavior MUST align with Ant Design interaction patterns
- **English Language Default:** The user interface MUST display all text, labels, error messages, and notifications in English language by default
- **No Internationalization (i18n):** Multi-language support is NOT implemented in the current version; all UI text is HARDCODED in English
- **Accessibility Limitations:** The system MUST meet basic accessibility requirements (keyboard navigation, semantic HTML) but is NOT required to meet WCAG 2.1 AA compliance

### 1.5.4.3. Browser Dependency Constraints

- **JavaScript Requirement:** The application REQUIRES JavaScript to be enabled in the browser; no-JavaScript fallback is NOT provided
- **LocalStorage Dependency:** JWT token persistence REQUIRES browser LocalStorage with minimum **5 MB** quota; browsers with disabled LocalStorage CANNOT maintain authenticated sessions
- **Modern Browser Features:** The application DEPENDS on modern browser APIs (Fetch API, ES6+ JavaScript, WebSocket, LocalStorage); legacy browser support (Internet Explorer) is NOT provided

## 1.5.5. Regulatory and Compliance Constraints

### 1.5.5.1. Data Sovereignty Constraints

- **On-Premise Data Storage:** All application data (user records, attendance logs, chat messages, financial records) MUST remain within the organization's designated server infrastructure
- **No External Data Transmission:** The system SHALL NOT transmit any operational data to external third-party services, cloud telemetry platforms, or analytics services without explicit administrator configuration
- **No Cloud Dependencies:** The system MUST operate independently without requiring internet connectivity to external cloud services (authentication providers, CDNs, API services)
- **Data Export Control:** Organizations MUST have complete control over data export, backup, and migration; vendor lock-in through proprietary data formats is PROHIBITED

### 1.5.5.2. Audit and Logging Constraints

- **Critical Action Logging:** The following critical actions MUST be logged in the database with timestamp and user identification:
  - User authentication (login, logout, password changes)
  - Attendance clock-in and clock-out events
  - Task status changes (pending → in_progress → completed)
  - Financial allowance creation and modifications
  - User account creation, modification, and deletion
  - System settings changes
- **Audit Trail Immutability:** Logged audit records MUST NOT be modifiable or deletable through the application interface; database-level protections SHOULD be implemented
- **Log Retention:** Audit logs MUST be retained for minimum **90 days**; longer retention periods MAY be configured based on organizational policies
- **No Automatic Log Deletion:** The system SHALL NOT automatically delete audit logs; log retention management is the responsibility of system administrators

### 1.5.5.3. Data Privacy Constraints

- **GDPR Considerations:** For deployments in jurisdictions subject to GDPR or similar privacy regulations:
  - User data deletion MUST be supported through admin interface
  - Data export functionality MUST be available for data portability
  - User consent for data processing MUST be documented (implementation responsibility of deploying organization)
- **Employee Data Protection:** Employee personal information (phone numbers, addresses, employment details) MUST be accessible only to authorized roles (admin, manager)
- **Chat Privacy:** Private chat conversations MUST be accessible only to conversation participants; system administrators SHALL NOT have built-in access to read private messages without database-level access

## 1.5.6. Deployment and Operational Constraints

### 1.5.6.1. Installation Constraints

- **Manual Installation Required:** The system REQUIRES manual installation and configuration by technically proficient administrators:
  - PostgreSQL database installation and configuration
  - Node.js runtime installation
  - Environment variable configuration (.env files)
  - Database schema initialization (setupDatabase.js)
  - Default admin account seeding (seedAdmin.js)
- **No Automated Installer:** The system does NOT provide graphical installer or automated setup wizard; command-line proficiency is REQUIRED
- **Configuration Management:** All configuration MUST be managed through environment variables; hardcoded configuration values in source code are PROHIBITED

### 1.5.6.2. Backup and Recovery Constraints

- **Manual Backup Responsibility:** Database backup is the responsibility of system administrators; automated backup scripts are NOT included in the base system
- **PostgreSQL Backup Tools:** Backups MUST be performed using PostgreSQL native tools (pg_dump, pg_basebackup); third-party backup solutions MAY be used at administrator discretion
- **No Built-In Backup UI:** The application does NOT provide user interface for backup management; all backup operations MUST be performed via command-line tools or scheduled tasks

### 1.5.6.3. Update and Maintenance Constraints

- **Manual Update Process:** System updates REQUIRE manual deployment of new application versions:
  - Git pull or file replacement for application code
  - npm install for dependency updates
  - Database migration scripts for schema changes
  - Application restart for changes to take effect
- **Downtime During Updates:** System updates MAY require application downtime; zero-downtime updates are NOT supported in the current architecture
- **Version Compatibility:** Database schema versions MUST be compatible with application code versions; mismatched versions MAY cause system failures

## 1.5.7. Integration Constraints

### 1.5.7.1. Third-Party Integration Limitations

- **No Built-In Integrations:** The system does NOT provide built-in integrations with:
  - Payroll systems
  - HR management systems
  - Time tracking services
  - Calendar applications (Google Calendar, Outlook)
  - Single Sign-On (SSO) providers
- **API-First Architecture:** External integrations MUST be implemented by consuming the RESTful API endpoints; no plugin architecture is provided
- **Email Service Dependency:** Password reset functionality REQUIRES SMTP email server configuration; the system does NOT include built-in email delivery

### 1.5.7.2. Data Import/Export Constraints

- **No Bulk Import UI:** The system does NOT provide user interface for bulk data import (CSV, Excel); initial data population MUST be performed via database scripts or API calls
- **Manual Data Export:** Data export MUST be performed via database queries or API endpoint consumption; no built-in export functionality is provided
- **No Data Migration Tools:** Migration from other workforce management systems MUST be performed manually; automated migration tools are NOT provided

## 1.5.8. Development and Maintenance Constraints

### 1.5.8.1. Code Organization Constraints

- **Modular Route Structure:** Backend API routes MUST be organized by functional module (auth, staff, tasks, attendance, reports, complaints, feedback, allowances, chat, profile, settings)
- **Component-Based Frontend:** React components MUST be organized by type (pages, components, utils) with clear separation of concerns
- **No Monolithic Files:** Individual source files MUST NOT exceed **500 lines of code**; large files MUST be refactored into smaller modules

### 1.5.8.2. Dependency Management Constraints

- **npm Package Manager:** All Node.js dependencies MUST be managed via npm; alternative package managers (yarn, pnpm) MAY be used but are NOT officially supported
- **Semantic Versioning:** Dependency versions MUST follow semantic versioning (semver) with explicit version constraints in package.json
- **Security Updates:** Dependencies with known security vulnerabilities MUST be updated promptly; automated dependency scanning is RECOMMENDED

### 1.5.8.3. Testing Constraints

- **No Comprehensive Test Suite:** The system does NOT include comprehensive automated tests (unit tests, integration tests, end-to-end tests)
- **Manual Testing Required:** System functionality MUST be verified through manual testing before production deployment
- **Test Framework Available:** Testing libraries (@testing-library/react, jest-dom) are INCLUDED but test implementation is NOT complete

## 1.5.9. Documentation Constraints

### 1.5.9.1. Technical Documentation Requirements

- **README Documentation:** The system MUST include README.md with:
  - Installation instructions
  - Configuration requirements
  - Default credentials
  - Troubleshooting guidance
- **Code Comments:** Complex business logic and non-obvious code sections MUST include explanatory comments
- **API Documentation:** RESTful API endpoints SHOULD be documented with request/response formats; formal API documentation (OpenAPI/Swagger) is NOT required

### 1.5.9.2. User Documentation Constraints

- **No Built-In Help System:** The application does NOT include contextual help, tooltips, or user guides within the interface
- **External Documentation:** User training and documentation is the responsibility of the deploying organization
- **Admin Responsibility:** System administrators MUST provide user training and support; no vendor support is included

## 1.5.10. Licensing and Distribution Constraints

### 1.5.10.1. Open Source Constraints

- **Dependency Licensing:** All third-party dependencies MUST use permissive open-source licenses (MIT, Apache 2.0, BSD) compatible with commercial deployment
- **No GPL Dependencies:** GNU General Public License (GPL) dependencies MUST be avoided to prevent copyleft licensing obligations
- **License Compliance:** Deploying organizations MUST comply with all third-party dependency licenses

### 1.5.10.2. Deployment Restrictions

- **Self-Hosted Only:** The system is DESIGNED for self-hosted deployment; Software-as-a-Service (SaaS) multi-tenant deployment is NOT supported in the current architecture
- **Single-Tenant Architecture:** Each deployment MUST serve a single organization; multi-tenant data isolation is NOT implemented
- **No Usage Restrictions:** Once deployed, there are NO restrictions on number of users, transactions, or data volume (subject to hardware constraints)
