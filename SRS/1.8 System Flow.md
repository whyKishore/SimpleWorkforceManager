# 1.8. System Flow

This section details the operational workflows for authentication, daily tasks, communication, and administration within the Simple Workforce Manager system. Each flow describes the sequential steps users take to interact with the system's core modules, illustrating the flow of data and control between the User, Frontend (React), and Backend (Express.js/PostgreSQL). These workflows represent the actual implementation as deployed in the PERN stack architecture with Socket.io for real-time communication.

The flows are organized by functional area and demonstrate how the three-tier role hierarchy (Admin, Manager, Staff) interacts with the system through role-specific interfaces and operations. Each workflow includes conditional logic, error handling, and success paths that reflect the production system behavior.

## 1.8.0. Application Initialization Flow

### Scenario
User opens the application for the first time or returns to the application with an existing session.

### Flow Steps

**Step 1: User Accesses Application URL**
- User navigates to http://localhost:3000 or LAN IP address
- Browser loads React application
- App.js component mounts and initializes

**Step 2: Application Checks for Existing Session**
- App.js useState hooks initialize:
  - user state: null (no user loaded yet)
  - isLoading state: true (loading in progress)
- useEffect hook executes on component mount
- System checks browser LocalStorage for JWT token
- const storedToken = localStorage.getItem("token")

**Step 3: Token Found - Restore Session**
- If storedToken exists:
  - connectSocket(storedToken) initiates WebSocket connection
  - Socket.io client connects to backend
  - Client emits 'authenticate' event with token
  - Backend verifies token and stores user_id → socket_id mapping
  - fetchUserProfile() executes to retrieve user data
  - Axios GET request to /api/profile/me
  - Authorization header includes stored token
- setIsLoading(false) completes initialization

**Step 4: Backend Validates Token and Returns Profile**
- authenticateToken middleware verifies JWT token
- If token valid:
  - Backend LEFT JOINs users with user_profiles
  - Response: Complete user profile with all fields
  - Frontend setUser(res.data) stores user in state
- If token invalid or expired:
  - Backend returns 401 Unauthorized
  - Frontend catch block executes handleLogout()
  - localStorage.removeItem("token") clears invalid token
  - setUser(null) clears user state
  - disconnectSocket() closes WebSocket

**Step 5: Application Renders Based on Authentication State**
- If isLoading === true:
  - Display: "Loading..." message
  - User waits for initialization to complete
- If user === null:
  - React Router renders public routes only
  - Available routes: /login, /forgot-password, /reset-password/:token
  - All other routes redirect to /login
- If user !== null:
  - Check user.is_default_password flag
  - If true: Render ResetPasswordPage (forced password change)
  - If false: Render authenticated application with role-based routes

**Step 6: Role-Based Menu Generation**
- buildMenuItems() function executes with user object
- Base links available to all authenticated users:
  - Dashboard (/)
  - Chat (/chat)
  - My Profile (/profile)
  - Settings (/settings)
- Role-specific links added based on user.role:
  - **Staff**: My Tasks (/tasks)
  - **Manager**: View Attendance, View Reports, Manage Allowances, Manage Tasks, View Complaints, View Feedback
  - **Admin**: Manage Staff, View Complaints, View Feedback
- Ant Design Menu component renders with role-appropriate items

**Step 7: Header and Layout Rendering**
- If user authenticated:
  - Ant Design Layout with Header and Content
  - Header displays:
    - Company name/logo: "SWM" (Title level 4)
    - Horizontal navigation menu (centered)
    - User avatar (first character of first_name or username)
    - User name display: "First (username)" or "username"
    - Logout button (primary ghost type)
  - Content area with padding: 24px 48px
  - React Router Routes render based on current path
- If user not authenticated:
  - No header displayed
  - Content area renders login/password reset pages

**Step 8: No Token Found - Redirect to Login**
- If storedToken === null:
  - setIsLoading(false) completes initialization
  - user remains null
  - React Router redirects all routes to /login
  - Login component renders
  - User must authenticate to access application

### Alternative Flow: Token Expired During Session

**Step 4a: Token Expires While User Active**
- User makes API request with expired token (after 1 hour)
- Backend jwt.verify() throws TokenExpiredError
- Middleware returns 401 "Token is not valid"
- Axios interceptor catches 401 response
- Frontend redirects to /login
- User must log in again to continue

### Alternative Flow: Page Refresh

**Step 1a: User Refreshes Browser**
- Browser reloads application
- React application re-initializes
- App.js useEffect executes again
- Token retrieved from LocalStorage (if exists)
- Session restored automatically
- User returns to same authenticated state
- No re-login required (if token still valid)

## 1.8.1. Login and Authentication Flow

### Scenario
A user accessing the Simple Workforce Manager system for the first time or returning to the application.

### Primary Flow: Standard Login

**Step 1: User Accesses Login Page**
- User navigates to application URL (http://localhost:3000 or LAN IP)
- Frontend checks browser LocalStorage for existing JWT token
- If no token found, React Router redirects to /login route
- Login component renders with Ant Design Card and Form components

**Step 2: User Enters Credentials**
- User inputs username in text field (Ant Design Input with UserOutlined icon)
- User inputs password in password field (Ant Design Input.Password with LockOutlined icon)
- Form validation ensures both fields are required
- User clicks "Log in" button (Button component with loading state)

**Step 3: Frontend Submits Login Request**
- Form onFinish handler triggers with validated values
- setLoading(true) activates button loading spinner
- Axios POST request sent to /api/auth/login endpoint
- Request body: { username, password }
- Authorization header not required for login endpoint

**Step 4: Backend Validates Credentials**
- Express route handler receives POST /api/auth/login request
- System validates username and password fields are provided
- Database query: SELECT * FROM users WHERE username = $1
- If user not found, return 401 "Invalid credentials"
- BCrypt comparison: bcrypt.compare(provided_password, stored_password_hash)
- If password mismatch, return 401 "Invalid credentials"

**Step 5: Backend Generates JWT Token**
- System constructs JWT payload: { user: { id, role, is_default_password } }
- Token signed with JWT_SECRET and 1-hour expiration
- Response: { message: "Login successful!", token: "<jwt_token>" }
- HTTP 200 status code returned

**Step 6: Frontend Processes Successful Login**
- onLoginSuccess callback receives JWT token
- Token stored in browser LocalStorage: localStorage.setItem("token", token)
- connectSocket(token) initiates WebSocket connection
- Socket.io client connects and emits 'authenticate' event with token
- fetchUserProfile() API call: GET /api/profile/me
- User profile data retrieved and stored in React state

**Step 7: System Checks Default Password Flag**
- If user.is_default_password === true:
  - App.js conditional renders ResetPasswordPage component
  - User cannot access main application until password changed
  - Proceed to Mandatory Password Change Flow (Section 1.8.1.1)
- If user.is_default_password === false:
  - Proceed to Step 8 (Role-Based Dashboard Redirect)

**Step 8: Role-Based Dashboard Redirect**
- React Router navigates to "/" (dashboard route)
- App.js buildMenuItems() generates role-specific navigation menu
- DashboardPage component renders with role-specific content:
  - **Staff**: Two-column layout with Staff Actions Card and ClockInWidget
  - **Manager**: Welcome card with navigation instructions
  - **Admin**: Welcome card with navigation instructions
- Header displays user avatar, name, and logout button
- Navigation menu shows role-appropriate links

### Alternative Flow 1: Invalid Credentials

**Step 4a: Backend Returns Error**
- If username not found or password mismatch
- Response: 401 status with { message: "Invalid credentials" }

**Step 6a: Frontend Displays Error**
- Catch block in onFinish handler executes
- setLoading(false) deactivates button spinner
- setError() updates error state with message
- Ant Design Alert component displays error message (red, with icon)
- User remains on login page to retry

### Alternative Flow 2: Server Error

**Step 4b: Backend Exception Occurs**
- Database connection failure or unexpected error
- Response: 500 status with { message: "Server error during login" }

**Step 6b: Frontend Displays Generic Error**
- Error message: "Login failed. Please try again."
- User remains on login page to retry


## 1.8.1.1. Mandatory Password Change Flow

### Scenario
User with is_default_password=true flag must change password before accessing the system.

### Flow Steps

**Step 1: System Detects Default Password**
- After successful login, App.js checks user.is_default_password
- Conditional rendering: if (user?.is_default_password) return <ResetPasswordPage />
- User cannot access any other routes until password changed

**Step 2: User Views Password Reset Page**
- ResetPasswordPage component renders with form
- Form fields: New Password (minimum 6 characters)
- Submit button: "Reset Password"
- No navigation menu displayed (forced flow)

**Step 3: User Submits New Password**
- User enters new password (minimum 6 characters validation)
- Form submission triggers handleSubmit function
- Axios POST request to /api/auth/reset-password
- Authorization header includes JWT token from login
- Request body: { newPassword }

**Step 4: Backend Validates and Updates Password**
- authenticateToken middleware verifies JWT token
- System validates newPassword length >= MIN_PASSWORD_LENGTH (6)
- BCrypt salt generation: bcrypt.genSalt(10)
- Password hashing: bcrypt.hash(newPassword, salt)
- Database UPDATE: SET password_hash = $1, is_default_password = false WHERE user_id = $2
- Response: 200 status with { message: "Password reset successful. Please log in again." }

**Step 5: Frontend Forces Re-Login**
- Success message displayed to user
- onPasswordReset callback executes handleLogout()
- localStorage.removeItem("token") clears JWT
- disconnectSocket() closes WebSocket connection
- setUser(null) clears user state
- React Router redirects to /login
- User must log in again with new credentials

**Step 6: User Logs In with New Password**
- User enters username and new password
- Standard login flow executes (Section 1.8.1)
- is_default_password now false, user proceeds to dashboard

## 1.8.1.2. Logout Flow

### Scenario
Authenticated user wants to end their session and log out of the system.

### Flow Steps

**Step 1: User Clicks Logout Button**
- User clicks "Logout" button in application header
- Button type: primary ghost (white text on dark background)
- onClick handler triggers handleLogout() function

**Step 2: Frontend Clears Session Data**
- handleLogout() function executes (defined with useCallback)
- localStorage.removeItem("token") removes JWT token from browser storage
- setUser(null) clears user state in React
- disconnectSocket() closes WebSocket connection

**Step 3: WebSocket Disconnection**
- Socket.io client disconnect() method called
- Client sends disconnect event to server
- Server receives disconnect event
- Server executes disconnect handler:
  - getUserIdFromSocket(socket.id) retrieves user ID
  - userSocketMap.delete(userId) removes user-socket mapping
  - Console log: "User disconnected: [socket.id]"
- WebSocket connection closed

**Step 4: Application State Reset**
- user state now null
- React re-renders application
- Conditional rendering in App.js detects user === null
- Header component unmounts (no longer displayed)
- Navigation menu removed

**Step 5: Redirect to Login Page**
- React Router detects unauthenticated state
- All protected routes redirect to /login
- Login component renders
- User sees login form
- Session completely terminated

**Step 6: User Must Re-authenticate**
- User cannot access any protected routes
- Attempting to navigate to any route redirects to /login
- User must enter credentials again to access system
- Previous session data cleared
- New login creates new JWT token and WebSocket connection

### Security Considerations

**Token Invalidation:**
- JWT token removed from client storage
- Token cannot be used for future requests
- Server-side token remains valid until expiration (1 hour)
- No server-side token blacklist (stateless authentication)
- Token naturally expires after 1 hour if not used

**WebSocket Cleanup:**
- User-socket mapping removed from server memory
- No messages can be delivered to disconnected user
- User must reconnect WebSocket on next login
- Prevents message delivery to logged-out users

**State Cleanup:**
- All React state cleared (user, messages, conversations, etc.)
- No sensitive data remains in browser memory
- LocalStorage only stores token (now removed)
- Clean slate for next login

## 1.8.1.3. Forgot Password Flow

### Scenario
User cannot remember password and requests reset via email.

### Flow Steps

**Step 1: User Accesses Forgot Password Page**
- User clicks "Forgot your password?" link on login page
- React Router navigates to /forgot-password
- ForgotPasswordPage component renders with email input form

**Step 2: User Submits Email Address**
- User enters email address in form field
- Form validation ensures email field is required
- User clicks submit button
- Axios POST request to /api/auth/forgot-password
- Request body: { email }

**Step 3: Backend Processes Reset Request**
- System queries database: SELECT * FROM users WHERE email = $1
- If user not found, return generic success message (security: prevent email enumeration)
- If user found:
  - Generate cryptographically secure token: crypto.randomBytes(32).toString('hex')
  - Calculate expiration: NOW() + 15 minutes
  - Database UPDATE: SET password_reset_token = $1, password_reset_expires = $2
  - Construct reset URL: ${FRONTEND_URL}/reset-password/${token}
  - Send email via nodemailer with reset link
- Response: 200 status with generic message "If an account with that email exists, a reset link has been sent."

**Step 4: User Receives Email**
- Email delivered to user's inbox (if account exists)
- Email contains reset link with embedded token
- Link expires after 15 minutes
- User clicks link in email

**Step 5: User Accesses Reset Confirmation Page**
- Browser navigates to /reset-password/:token
- PerformResetPage component renders
- Token extracted from URL parameter
- Form displays: New Password input field

**Step 6: User Submits New Password**
- User enters new password
- Form submission triggers handleSubmit
- Axios POST request to /api/auth/perform-reset
- Request body: { token, newPassword }

**Step 7: Backend Validates Token and Updates Password**
- System queries: SELECT * FROM users WHERE password_reset_token = $1 AND password_reset_expires > NOW()
- If token invalid or expired, return 400 "Password reset token is invalid or has expired"
- If token valid:
  - Generate BCrypt salt and hash new password
  - Database UPDATE: SET password_hash = $1, password_reset_token = NULL, password_reset_expires = NULL, is_default_password = false
- Response: 200 status with { message: "Password reset successful. You can now log in." }

**Step 8: User Redirected to Login**
- Success message displayed
- React Router navigates to /login
- User logs in with new password

## 1.8.2. Daily Operations Flow (Attendance)

### Scenario
Staff member starting their workday and tracking attendance.

### Flow Steps

**Step 1: Staff Logs In**
- Staff completes login flow (Section 1.8.1)
- System redirects to staff dashboard (/)
- DashboardPage component renders with two-column layout

**Step 2: Staff Views Dashboard**
- Left column: Staff Actions Card with quick links
- Right column: ClockInWidget component
- ClockInWidget fetches current status on mount

**Step 3: ClockInWidget Fetches Status**
- useEffect hook triggers on component mount
- Axios GET request to /api/attendance/status
- Backend queries: SELECT * FROM attendance WHERE user_id = $1 AND attendance_date = CURRENT_DATE AND clock_out_time IS NULL
- Response: { isClockedIn: boolean, record: {...} }
- Widget displays current status: "You are currently clocked in" or "You are currently clocked out"

**Step 4: Staff Clicks "Clock In" Button**
- User clicks primary button (blue) labeled "Clock In"
- handleClockIn function executes
- setMessage("") and setError("") clear previous feedback
- Axios POST request to /api/attendance/clock-in
- Authorization header includes JWT token

**Step 5: Backend Validates Clock-In Request**
- authenticateToken middleware verifies JWT
- checkRole middleware ensures user role is 'staff'
- System queries for existing active session: WHERE user_id = $1 AND attendance_date = CURRENT_DATE AND clock_out_time IS NULL
- If active session exists, return 409 "You are already clocked in"
- If no active session:
  - Database INSERT: INSERT INTO attendance (user_id) VALUES ($1) RETURNING *
  - Database automatically sets: attendance_date = CURRENT_DATE, clock_in_time = CURRENT_TIMESTAMP
- Response: 201 status with { message: "Clocked in successfully", attendance: {...} }

**Step 6: Frontend Updates UI**
- Success response triggers fetchStatus() to refresh widget
- Widget re-fetches status from /api/attendance/status
- isClockedIn now true
- Widget displays: "You are currently clocked in"
- Button changes to "Clock Out" (danger/red button)
- Success Alert displays: "Clocked in successfully!" (green)

**Step 7: Staff Works During Day**
- Staff navigates to other pages (tasks, chat, etc.)
- ClockInWidget remains on dashboard
- Attendance record persists in database with clock_in_time

**Step 8: Staff Returns to Dashboard at End of Day**
- Staff navigates back to dashboard (/)
- ClockInWidget fetches status again
- Widget displays "You are currently clocked in" with "Clock Out" button

**Step 9: Staff Clicks "Clock Out" Button**
- User clicks danger button (red) labeled "Clock Out"
- handleClockOut function executes
- Axios POST request to /api/attendance/clock-out

**Step 10: Backend Processes Clock-Out**
- System queries for active session: WHERE user_id = $1 AND attendance_date = CURRENT_DATE AND clock_out_time IS NULL
- If no active session, return 400 "You are not clocked in"
- If active session found:
  - Retrieve attendance_id
  - Database UPDATE: SET clock_out_time = CURRENT_TIMESTAMP WHERE attendance_id = $1 RETURNING *
- Response: 200 status with { message: "Clocked out successfully", attendance: {...} }

**Step 11: Frontend Updates UI**
- Success response triggers fetchStatus()
- isClockedIn now false
- Widget displays: "You are currently clocked out"
- Button changes back to "Clock In" (primary/blue button)
- Success Alert displays: "Clocked out successfully!" (green)

**Step 12: System Calculates Work Duration**
- Duration calculated as: clock_out_time - clock_in_time
- Calculation performed at query time or application layer
- Manager can view attendance records with duration in AttendancePage

### Alternative Flow: Duplicate Clock-In Attempt

**Step 5a: Active Session Already Exists**
- Backend finds existing record with clock_out_time IS NULL
- Response: 409 status with { message: "You are already clocked in" }
- Frontend displays error Alert: "You are already clocked in" (red)
- Widget remains in clocked-in state

### Alternative Flow: Clock-Out Without Clock-In

**Step 10a: No Active Session Found**
- Backend finds no record with clock_out_time IS NULL
- Response: 400 status with { message: "You are not clocked in" }
- Frontend displays error Alert: "You are not clocked in" (red)
- Widget remains in clocked-out state


## 1.8.3. Task Execution Workflow

### Scenario
Manager assigning work to staff and staff member completing assigned tasks.

### Part A: Task Assignment by Manager

**Step 1: Manager Navigates to Task Management**
- Manager logs in and accesses dashboard
- Manager clicks "Manage Tasks" in navigation menu
- React Router navigates to /manage-tasks
- ProtectedRoute verifies user role is 'manager'
- ManageTasksPage component renders

**Step 2: Manager Views Existing Tasks**
- Component mount triggers fetchData() via useEffect
- Promise.all executes two parallel API calls:
  - GET /api/tasks/ - Retrieves all tasks
  - GET /api/staff/ - Retrieves all staff members
- Backend LEFT JOINs tasks with users table (twice for assignee and assigner)
- Tasks ordered by created_at DESC (newest first)
- Ant Design Table displays tasks with columns: Title, Assigned To, Status, Due Date, Actions

**Step 3: Manager Clicks "Assign New Task" Button**
- showCreateModal() function executes
- setIsEditing(false) sets mode to create
- form.resetFields() clears any previous data
- form.setFieldsValue({ status: 'pending' }) sets default status
- setIsModalVisible(true) opens modal dialog
- Modal title: "Assign New Task"

**Step 4: Manager Fills Task Form**
- Form fields displayed in modal:
  - Task Title (Input, required)
  - Description (Input.TextArea, optional)
  - Assign To (Select dropdown, required)
  - Status (Select dropdown, required, default: 'pending')
  - Due Date (DatePicker, optional)
- Staff dropdown populated from staffList (filtered to role='staff')
- Staff displayed as: "First Last (username)"
- Manager selects staff member from dropdown
- Manager enters task title and description
- Manager selects due date (optional)
- Manager keeps status as 'pending' or changes to 'in_progress'

**Step 5: Manager Submits Task**
- User clicks "Assign Task" button
- handleFormSubmit function executes with form values
- Due date converted to ISO string: values.due_date.toISOString()
- Axios POST request to /api/tasks/
- Request body: { title, description, assigned_to, status, due_date }
- Authorization header includes JWT token

**Step 6: Backend Creates Task**
- authenticateToken middleware verifies JWT
- checkRole middleware ensures role is 'admin' or 'manager'
- System validates title and assigned_to are provided
- System retrieves assigned_by from JWT token (req.user.id)
- System verifies assigned_to user exists: SELECT role FROM users WHERE user_id = $1
- If user not found, return 404 "Assigned user does not exist"
- Database INSERT: INSERT INTO tasks (title, description, assigned_to, assigned_by, due_date) VALUES (...) RETURNING *
- Database automatically sets: status='pending', created_at=CURRENT_TIMESTAMP
- Response: 201 status with complete task object

**Step 7: Frontend Updates Task List**
- Success message displayed: "Task assigned successfully"
- setIsModalVisible(false) closes modal
- fetchData() called to refresh task list
- New task appears in table with assigned staff username
- Manager sees updated task list

### Part B: Task Execution by Staff

**Step 8: Staff Views Assigned Tasks**
- Staff logs in and navigates to dashboard
- Staff clicks "View My Tasks" link or "My Tasks" in navigation
- React Router navigates to /tasks
- MyTasksPage component renders

**Step 9: Staff Fetches Personal Tasks**
- useEffect triggers fetchMyTasks() on mount
- Axios GET request to /api/tasks/mytasks
- Backend queries: SELECT t.*, u.username AS assigned_by_username FROM tasks t LEFT JOIN users u ON t.assigned_by = u.user_id WHERE t.assigned_to = $1 ORDER BY t.created_at DESC
- Response: Array of tasks assigned to authenticated user
- Ant Design List displays tasks with vertical item layout

**Step 10: Staff Views Task Details**
- Each task displays:
  - Title (Typography Title level 4)
  - Description (Typography Paragraph)
  - Assigned by username
  - Due date (formatted with user's date_format preference)
  - Status tag (color-coded: Blue=pending, Orange=in_progress, Green=completed)
  - Status dropdown (Ant Design Select)

**Step 11: Staff Updates Task Status to "In Progress"**
- Staff clicks status dropdown on a pending task
- Dropdown shows three options: Pending, In Progress, Completed
- Staff selects "In Progress"
- handleStatusChange function executes with (task_id, 'in_progress')
- Axios PATCH request to /api/tasks/:id/status
- Request body: { status: 'in_progress' }

**Step 12: Backend Updates Task Status**
- authenticateToken middleware verifies JWT
- checkRole middleware ensures role is 'staff'
- System validates status field is provided
- System validates status is valid ENUM value
- Database UPDATE: SET status = $1 WHERE task_id = $2 AND assigned_to = $3 RETURNING *
- Critical security filter: AND assigned_to = current_user_id prevents updating other users' tasks
- If no rows updated, return 404 "Task not found or permission denied"
- Response: 200 status with updated task object

**Step 13: Frontend Updates UI**
- Success message: "Task status updated"
- setTasks updates state with new status
- Task status tag changes from Blue (pending) to Orange (in_progress)
- Dropdown reflects new status
- No page refresh required

**Step 14: Staff Works on Task**
- Staff performs work related to task
- Task remains in "In Progress" status
- Staff can view task details anytime

**Step 15: Staff Completes Task**
- Staff returns to My Tasks page
- Staff clicks status dropdown on in-progress task
- Staff selects "Completed"
- handleStatusChange executes with (task_id, 'completed')
- Same PATCH request flow as Step 11-12
- Status tag changes to Green (completed)

**Step 16: Manager Views Updated Task**
- Manager navigates to Manage Tasks page
- fetchData() retrieves all tasks including updated one
- Manager sees task status changed to "Completed"
- Manager sees completion reflected in real-time (on next page load)
- Task list shows updated status with green tag

### Alternative Flow: Manager Edits Existing Task

**Step 3a: Manager Clicks "Edit" Button**
- Manager clicks "Edit" link button in Actions column
- showEditModal(task) function executes
- setIsEditing(true) sets mode to edit
- setEditingTaskId(task.task_id) stores task ID
- form.setFieldsValue() pre-populates form with existing task data
- Due date converted to Moment object for DatePicker
- Modal title: "Edit Task"

**Step 5a: Manager Updates Task**
- Manager modifies any fields (title, description, assignee, status, due date)
- Manager can reassign task to different staff member
- Manager can manually change status
- User clicks "Update Task" button
- Axios PUT request to /api/tasks/:id
- Request body includes all fields (title, description, assigned_to, status, due_date)

**Step 6a: Backend Updates Task**
- checkRole middleware ensures role is 'manager'
- System validates all required fields
- Database UPDATE: SET all fields WHERE task_id = $1 RETURNING *
- Response: 200 status with updated task
- Frontend displays: "Task updated successfully"

### Alternative Flow: Manager Deletes Task

**Step 3b: Manager Clicks "Delete" Button**
- Manager clicks "Delete" link button (danger type) in Actions column
- handleDelete(task_id) function executes
- Confirmation dialog: window.confirm("Are you sure you want to delete this task?")
- If user cancels, operation aborted
- If user confirms, Axios DELETE request to /api/tasks/:id

**Step 6b: Backend Deletes Task**
- checkRole middleware ensures role is 'manager'
- Database DELETE: DELETE FROM tasks WHERE task_id = $1 RETURNING title
- Response: 200 status with { message: "Task '[title]' deleted successfully" }
- Frontend displays success message
- fetchData() refreshes task list
- Task removed from table


## 1.8.4. Communication & Grievance Flow

### Scenario
Staff member needing to communicate with colleagues or report issues through various channels (Chat, Reports, Complaints, Feedback).

### Part A: Real-Time Chat Communication

**Step 1: User Accesses Chat Interface**
- User (any role) clicks "Chat" in navigation menu
- React Router navigates to /chat
- ChatPage component renders with three-panel layout
- Sidebar (30% width): Contacts/Search/Blocked views
- Chat Window (70% width): Message display and input

**Step 2: User Searches for Colleague**
- User enters search query in search form (username or email)
- handleSearch function executes on form submit
- Axios GET request to /api/chat/search?query=<term>
- Backend performs case-insensitive ILIKE search on username and email
- Backend LEFT JOINs with user_profiles for full names
- Backend excludes current user from results
- Response: Array of matching users
- Search results displayed in sidebar with clickable user cards

**Step 3: User Selects Conversation Partner**
- User clicks on search result or existing contact
- selectUserToChat(user) function executes
- setSelectedUser stores selected user information
- Axios GET request to /api/chat/history/:userId
- Backend normalizes user pairing: user1_id = MIN(current_user, other_user), user2_id = MAX(current_user, other_user)

**Step 4: Backend Retrieves Conversation History**
- System queries conversations table: WHERE user1_id = $1 AND user2_id = $2
- If no conversation exists, return { conversation: null, messages: [] }
- If conversation exists:
  - Check conversation status
  - If status='blocked', return 403 "This conversation is blocked"
  - Determine cleared_at timestamp based on current user position
  - Query messages: WHERE conversation_id = $1 AND sent_at > cleared_at ORDER BY sent_at ASC
- Response: { conversation: {...}, messages: [...] }

**Step 5: Frontend Displays Chat Window**
- setCurrentConvo stores conversation object
- setMessages stores message array

**Step 8: Backend Delivers Message to Recipient**
- System retrieves receiver socket_id from userSocketMap

**Step 10: Recipient's Frontend Updates (Real-Time)**

- handleReceiveMessage function executes
- If message is for currently open conversation:

- If any operation fails, transaction rolls back: client.query("ROLLBACK")

- User clicks "Change Password" section
- Form displays with three fields:
  - Old Password (Input.Password, required)
  - New Password (Input.Password, required, minimum 6 characters)
  - Confirm New Password (Input.Password, required, must match)
- User enters current password and new password
- User clicks "Change Password" button

**Step 26: Backend Validates and Updates Password**
- Axios PUT request to /api/settings/change-password
- Request body: { oldPassword, newPassword }
- Backend retrieves current password_hash from database
- BCrypt comparison: bcrypt.compare(oldPassword, stored_hash)
- If old password incorrect, return 401 "Incorrect old password"
- If old password correct:
  - Generate new salt: bcrypt.genSalt(10)
  - Hash new password: bcrypt.hash(newPassword, salt)
  - Database UPDATE: SET password_hash = $1 WHERE user_id = $2
- Response: 200 status with { message: "Password changed successfully" }

**Step 27: Frontend Confirms Password Change**
- Success message displayed: "Password changed successfully"
- User remains logged in (no forced logout)
- User can continue using system with new password
- Next login requires new password

### Part D: User Profile Management

**Step 28: User Updates Personal Profile**
- User clicks "My Profile" in navigation menu
- React Router navigates to /profile
- ProfilePage component renders
- Component fetches current profile: GET /api/profile/me
- Form pre-populated with existing data

**Step 29: User Modifies Profile Information**
- User can update:
  - Username (unique constraint)
  - Email (unique constraint)
  - First Name
  - Last Name
  - Phone Number (unique constraint)
  - Job Title
  - Hire Date
  - Address
  - Sex
- User modifies desired fields
- User clicks "Update Profile" button

**Step 30: Backend Updates Profile with Transaction**
- Axios PUT request to /api/profile/me
- Request body: { username, email, first_name, last_name, phone_number, job_title, hire_date, address, sex }
- Database transaction begins
- If username or email provided, UPDATE users table
- UPSERT on user_profiles table: INSERT ... ON CONFLICT (user_id) DO UPDATE
- If unique constraint violated:
  - Identify specific constraint (username, email, or phone_number)
  - Return 409 with specific error message
- If successful, transaction commits
- Response: 200 status with updated profile

**Step 31: Frontend Confirms Profile Update**
- Success message displayed
- Profile form updates with new values
- Avatar updates if first_name changed (first character)
- Header displays updated name
- User sees changes reflected immediately

## 1.8.6. Cross-Cutting Flows

### Session Management Flow

**Token Expiration Handling:**
1. JWT token expires after 1 hour
2. User attempts API request with expired token
3. Backend jwt.verify() throws error
4. Middleware returns 401 "Token is not valid"
5. Frontend Axios interceptor catches 401 error
6. User redirected to login page
7. localStorage token cleared
8. Socket.io connection disconnected
9. User must log in again to continue

**Automatic Token Attachment:**
1. User logs in successfully
2. Token stored in localStorage
3. Axios request interceptor configured
4. Every API request automatically includes: Authorization: Bearer <token>
5. No manual token management required in components
6. Consistent authentication across all requests

### Real-Time Update Flow

**WebSocket Connection Lifecycle:**
1. User logs in successfully
2. connectSocket(token) called with JWT token
3. Socket.io client connects to backend
4. Client emits 'authenticate' event with token
5. Server verifies token and stores user_id → socket_id mapping
6. Connection maintained for session duration
7. Real-time events flow bidirectionally
8. On logout, disconnectSocket() closes connection
9. Server removes user_id → socket_id mapping

**Message Delivery Flow:**
1. Sender emits 'send_message' event
2. Server validates sender authentication
3. Server persists message in database
4. Server looks up receiver socket_id
5. If receiver online, server emits 'receive_message' to receiver
6. If receiver offline, message queued in database
7. Receiver retrieves messages on next login via history API
8. Callback confirms delivery to sender

### Error Handling Flow

**Client-Side Error Handling:**
1. API request fails (network error, server error, validation error)
2. Axios catch block executes
3. Error message extracted: err.response?.data?.message || fallback
4. Ant Design message.error() displays notification
5. Console.error() logs error for debugging
6. User sees user-friendly error message
7. Form remains populated for correction
8. Loading states reset to allow retry

**Server-Side Error Handling:**
1. Route handler wrapped in try-catch block
2. Error occurs (database error, validation error, etc.)
3. Catch block executes
4. Error logged: console.error()
5. Appropriate HTTP status code determined (400, 401, 403, 404, 409, 500)
6. User-friendly error message constructed
7. Response sent: { message: "..." }
8. Database transaction rolled back if applicable
9. Client receives error and displays to user

### Data Flow Patterns

**Request-Response Pattern:**
- Used for: CRUD operations, form submissions, data retrieval
- Flow: User action → Frontend validation → API request → Backend processing → Database operation → Response → UI update
- Examples: Login, create user, submit report, update task

**Real-Time Event Pattern:**
- Used for: Chat messaging, instant notifications
- Flow: User action → WebSocket emit → Server processing → Database persistence → WebSocket emit to recipient → UI update
- Examples: Send message, receive message

**Polling Pattern:**
- Used for: Status checks, data refresh
- Flow: Component mount → API request → Response → State update → UI render
- Examples: Fetch attendance status, fetch task list, fetch complaints

**Transaction Pattern:**
- Used for: Multi-table operations requiring atomicity
- Flow: API request → BEGIN transaction → Multiple database operations → COMMIT or ROLLBACK → Response
- Examples: Create user (users + user_profiles), update profile (users + user_profiles)

### State Management Patterns

**Component-Level State:**
- useState for local component data (form inputs, loading states, modal visibility)
- useEffect for data fetching on mount
- useCallback for memoized functions (prevent re-renders)

**Lifted State:**
- User object passed from App.js to all child components via props
- No global state management library (Redux, Context API)
- Props drilling for user data

**Form State:**
- Ant Design Form.useForm() hook manages form state

- form.getFieldsValue() for retrieval

**Persistent State:**
- JWT token in LocalStorage (survives page refresh)
- User session restored on application initialization
- No other persistent state (all data fetched from backend)
