# 1.7. System Features

This section provides a detailed breakdown of the specific capabilities of the 11 core modules within the Simple Workforce Manager system. These features ensure efficient management of workforce operations, user satisfaction through role-appropriate functionality, and operational transparency across all organizational levels. Each feature is designed to support the three-tier role hierarchy (Admin, Manager, Staff) while maintaining data security, integrity, and usability.

The system implements a comprehensive suite of features built on the PERN stack (PostgreSQL, Express.js, React 19, Node.js 18+) with real-time communication capabilities via Socket.io, stateless JWT authentication, and BCrypt password security. All features are accessible through a responsive web interface with role-based access control enforced at both the middleware and database levels.

## 1.7.1. Authentication & Authorization

### Description
The Authentication & Authorization module serves as the secure entry point for all users, implementing industry-standard security practices to protect user credentials and enforce role-based access control throughout the system.

### Functionalities

**JWT-Based Login/Logout:**
- Secure credential validation using BCrypt password comparison
- JWT token generation with 1-hour expiration for security
- Token payload includes user ID, role, and default password flag
- Client-side token storage in browser LocalStorage
- Automatic token attachment to all API requests via Axios interceptors
- Logout functionality clears token and disconnects WebSocket
- Generic error messages prevent user enumeration attacks

**Role-Based Access Control (RBAC):**
- Three-tier role hierarchy: Admin, Manager, Staff
- Middleware-enforced permissions on all protected endpoints
- Admin-exclusive access: User management, system settings
- Manager-exclusive access: Task assignment, attendance monitoring, allowance management
- Admin/Manager shared access: Complaints and feedback viewing/responding
- Staff-exclusive access: Task status updates, clock in/out, report/complaint/feedback submission
- All roles: Profile management, chat, personal settings
- 403 Forbidden responses with specific required roles for unauthorized access

**Forced Password Change on First Login:**
- Default password detection via is_default_password flag in JWT payload
- Mandatory password reset page displayed before system access
- Minimum password length validation (6 characters)
- BCrypt hashing with salt generation (10 rounds)
- is_default_password flag set to false after successful reset
- Forced logout and re-authentication with new credentials

**Secure "Forgot Password" Flow:**
- Email-based password reset request
- Cryptographically secure random token generation (32 bytes)
- Token expiration after 15 minutes (PASSWORD_RESET_EXPIRY_MINUTES)
- Password reset token and expiration stored in database
- Email delivery via nodemailer with SMTP configuration
- Reset URL construction: ${FRONTEND_URL}/reset-password/${token}
- Token validation on reset confirmation
- Password reset clears token and sets is_default_password to false
- Generic success messages regardless of email existence (security best practice)

### API Endpoints
- POST /api/auth/login - User authentication
- POST /api/auth/reset-password - Mandatory password change
- POST /api/auth/forgot-password - Password reset request
- POST /api/auth/perform-reset - Password reset confirmation

### Security Measures
- BCrypt password hashing with 10-round salt generation
- JWT tokens with 1-hour expiration
- Constant-time password comparison prevents timing attacks
- Parameterized SQL queries prevent SQL injection
- CORS configuration restricts cross-origin requests
- Password reset tokens expire after 15 minutes
- Generic error messages prevent user enumeration

## 1.7.3. User Management

### Description
The User Management module provides admin-centric functionality for managing the complete workforce roster, including user account creation, profile maintenance, and account lifecycle management with comprehensive data integrity controls. The StaffPage component provides a comprehensive interface for viewing and managing all non-admin users.

### Functionalities

**CRUD Operations for User Accounts:**
- **Create:** Admin-exclusive user account creation with transactional integrity
  - Required fields: username, email, password, role, first_name, last_name, phone_number, sex
  - Optional fields: job_title
  - BCrypt password hashing before storage
  - Automatic is_default_password flag set to true for new users
  - Atomic transaction ensures both user and profile created or neither
  - Unique constraint enforcement on username, email, phone_number
  - 409 Conflict responses with specific constraint details
- **Read:** Admin and Manager access to view user lists and details
  - View all non-admin users with LEFT JOIN to profiles
  - Comprehensive user details including hire_date and address
  - Filtered results exclude admin accounts for security
- **Update:** Admin-exclusive user account updates with transactional integrity
  - Update users table: username, email, role
  - UPSERT on user_profiles: first_name, last_name, phone_number, sex, job_title
  - Handles users without existing profiles gracefully
  - Unique constraint violation detection with specific error messages
  - Prevents updating admin accounts (role != 'admin' filter)
- **Delete:** Admin-exclusive user account deletion with cascade cleanup
  - Prevents deletion of admin accounts
  - CASCADE constraints automatically delete: user_profiles, attendance, reports, complaints, complaint_replies, feedback, allowances, conversations, messages
  - SET NULL constraints for tasks (assigned_to, assigned_by) and feedback (replied_by)
  - Returns deleted username for confirmation
  - 409 Conflict if foreign key constraint prevents deletion

**Extended Profile Fields:**
- Personal Information: first_name, last_name, phone_number, sex (ENUM: male, female, other)
- Employment Details: job_title, hire_date (DATE), address (TEXT)
- System Preferences: date_format (default: 'MM/DD/YYYY'), notification_prefs (JSONB)
- Profile data stored in separate user_profiles table with foreign key to users
- LEFT JOIN queries handle users without profiles gracefully
- UPSERT operations create profiles if missing during updates

**Data Integrity and Transaction Management:**
- Database transactions ensure atomic multi-table operations
- BEGIN → Multiple Operations → COMMIT (success) or ROLLBACK (failure)
- Connection pool management with client acquisition and release
- Unique constraints prevent duplicate usernames, emails, phone numbers
- Foreign key constraints maintain referential integrity
- CASCADE deletion ensures complete data cleanup
- SET NULL deletion preserves historical task and feedback records

### API Endpoints
- POST /api/staff/ - Create user account (Admin only)
- GET /api/staff/ - View all users (Admin, Manager)
- GET /api/staff/:id - View user details (Admin, Manager)
- PUT /api/staff/:id - Update user account (Admin only)
- DELETE /api/staff/:id - Delete user account (Admin only)

### Business Rules
1. Only admins can create, update, or delete user accounts
2. Managers can view user lists and details but cannot modify
3. Admin accounts cannot be updated or deleted via API
4. New users must change password on first login
5. Username, email, and phone number must be unique across system
6. User deletion triggers cascade cleanup of all related data
7. Task assignments preserved with NULL values when users deleted
8. All user operations logged with timestamps for audit trail

## 1.7.5. Attendance System

### Description
The Attendance System provides real-time tracking of employee working hours through a simple clock-in/clock-out interface, ensuring accurate time recording with server-side timestamp generation to prevent fraud and manipulation. The system features a prominent ClockInWidget component on the staff dashboard for easy access.

### Functionalities

**"One-Click" Clock In/Out Interface:**
- Staff-exclusive clock-in functionality via single button click
- Prominent ClockInWidget component displayed on staff dashboard
- Ant Design Card component with visual status indicators
- Color-coded buttons: Primary (blue) for Clock In, Danger (red) for Clock Out
- Automatic validation prevents duplicate clock-ins on same day
- 409 Conflict response if already clocked in
- Clock-out requires active clock-in session
- 400 Bad Request if attempting to clock out without active session
- Immediate feedback with Ant Design Alert components (success/error)
- Real-time status checking to display current clock-in state
- Loading spinner (Ant Design Spin) during status fetch
- Widget displays current status: "You are currently clocked in" or "You are currently clocked out"

**Server-Side UTC Timestamping:**
- All timestamps generated by PostgreSQL database server
- clock_in_time: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
- clock_out_time: TIMESTAMP set on clock-out action
- attendance_date: DATE DEFAULT CURRENT_DATE
- Prevents client-side time manipulation and fraud
- Consistent timezone handling (UTC) across all records
- Tamper-proof audit trail for compliance

**Daily Work Duration Calculation:**
- Automatic duration calculation: clock_out_time - clock_in_time
- Duration computed at query time or application layer
- Supports partial day tracking (clock in without clock out)
- NULL clock_out_time indicates active session
- Historical duration analysis for payroll and reporting

**Attendance History and Monitoring:**
- Manager and Admin access to all attendance records
- AttendancePage component with Ant Design Table layout
- LEFT JOIN with users table retrieves username for each record
- Table columns:
  - Staff Member (username)
  - Date (attendance_date with formatDate)
  - Clocked In (clock_in_time with formatDateTime)
  - Clocked Out (clock_out_time with formatDateTime or "N/A")
- Ordered by attendance_date DESC, clock_in_time DESC (most recent first)
- Comprehensive record details: attendance_id, user_id, username, clock_in_time, clock_out_time, attendance_date
- Date/time formatting respects user's date_format preference
- "N/A" displayed for null clock_out_time (active sessions)
- Loading spinner during data fetch
- Card component wrapper for consistent layout
- Staff can check current clock-in status via dedicated endpoint
- Historical records preserved for audit and compliance
- No pagination - displays all records
- Error handling with message.error() for failed fetches

**Clock-In Status Checking:**
- Real-time status endpoint for staff users
- Returns isClockedIn boolean flag
- Includes active attendance record if clocked in
- Enables UI to display current status and clock-in time
- Prevents duplicate clock-ins through status awareness

### API Endpoints
- POST /api/attendance/clock-in - Clock in (Staff)
- POST /api/attendance/clock-out - Clock out (Staff)
- GET /api/attendance/status - Check status (Staff)
- GET /api/attendance/all - View all attendance (Manager, Admin)

### Business Rules
1. Only staff can clock in and clock out
2. One active clock-in session per user per day
3. Must clock in before clocking out
4. All timestamps generated server-side (UTC)
5. Attendance records preserved when users deleted (CASCADE)
6. Managers and admins can view all attendance records
7. Staff can only view their own clock-in status
8. No manual timestamp editing allowed

## 1.7.6. Real-Time Communication (Chat)

### Description
The Real-Time Communication module implements an instant messaging system for internal collaboration, leveraging WebSocket technology via Socket.io to enable real-time bidirectional communication between users with message persistence and privacy controls.

### Functionalities

**1-on-1 Private Messaging via Socket.io:**
- WebSocket-based real-time message delivery
- Socket authentication with JWT token on connection
- In-memory user-socket mapping for instant routing (O(1) lookup)
- Message persistence in database regardless of recipient online status
- Automatic conversation creation on first message
- Normalized conversation pairing: user1_id < user2_id (ensures single conversation per pair)
- Real-time 'receive_message' event delivery to online recipients
- Callback acknowledgment for message delivery confirmation
- Offline message queuing - messages delivered as history on reconnection

**Message Persistence in Database:**
- All messages stored in messages table with foreign key to conversations
- Message fields: message_id, conversation_id, sender_id, content, sent_at
- Server-side sent_at timestamp (CURRENT_TIMESTAMP)
- Chronological message ordering (ORDER BY sent_at ASC)
- Message history retrieval with conversation context
- Messages preserved even if recipient offline
- No message size limit (TEXT column type)

**"Clear History" Privacy Feature:**
- Per-user message clearing without affecting other participant
- Conversation-level cleared_at timestamps: user1_cleared_at, user2_cleared_at
- Conditional timestamp update based on user position in conversation
- Messages remain in database but hidden from user who cleared
- Other participant's history unaffected
- New messages after clearing visible to both users
- Implements privacy without data loss

**Block/Unblock User Functionality:**
- Conversation status management: active/blocked (ENUM)
- Block conversation prevents further messages
- blocked_by field tracks who initiated block
- Only blocker can unblock conversation
- 403 Forbidden when attempting to message blocked conversation
- Unblock restores conversation to active status
- Block/unblock operations update conversation metadata only

**User Search and Discovery:**
- Search form with text input and submit button
- Case-insensitive partial matching on username and email (ILIKE)
- LEFT JOIN with user_profiles retrieves full names
- Excludes authenticated user from search results
- Returns: user_id, username, email, first_name, last_name
- Search results displayed in sidebar with clickable user cards
- User card format: "First Last (username)"
- No role restrictions - all users can search all users
- Enables finding conversation partners across organization
- Search query state management for dynamic results

**Conversation Management:**
- Three-panel layout: Sidebar (30% width), Chat Window (70% width)
- Sidebar views: "My Contacts", "Search Results", "Blocked"
- View list of all active conversations
- Conversation list includes other participant details
- Displays conversation status (active/blocked) and blocker identity
- Blocked by them indicator: Red text "(Blocked by them)"
- Conversation metadata: conversation_id, status, blocked_by
- Automatic conversation creation on first message exchange
- Unique constraint ensures single conversation per user pair
- Selected conversation highlighted with gray background (#eee)
- Blocked list shows count: "Blocked (X)"
- Unblock button available for conversations blocked by current user

**Chat Window Interface:**
- Empty state: "Select a contact or search for a user to start chatting."
- Chat header displays: "Chat with [First Name or Username]"
- Action buttons: "Clear Chat", "Block User" (red color)
- Message display area with scrollable container
- Messages aligned: Right (sent by current user), Left (received)
- Message bubbles: Green (#dcf8c6) for sent, White (#fff) for received
- Message content with timestamp below
- Timestamp format: formatDateTime with user's date_format preference
- Auto-scroll to bottom on new messages (messagesEndRef)
- Message input form at bottom with text input and Send button
- Input disabled when conversation blocked
- Placeholder text: "Type a message..." or "You cannot send messages." (if blocked)
- Error messages displayed in red at top of chat window
- Confirmation dialog for clear chat action

**WebSocket Connection Management:**
- Socket.io client connects on user login
- Automatic 'authenticate' event with JWT token
- Server verifies token and stores user_id → socket_id mapping
- Disconnect event removes mapping from memory
- Automatic reconnection handling by Socket.io client
- Single socket per user - new connection overwrites previous
- Real-time message reception via 'receive_message' event listener
- Callback acknowledgment for sent messages
- Error handling via 'chat_error' event listener

### API Endpoints and Socket Events

**HTTP Endpoints:**
- GET /api/chat/search?query=<term> - Search users
- GET /api/chat/conversations - View conversation list
- GET /api/chat/history/:userId - Retrieve message history
- PUT /api/chat/conversation/:convoId/block - Block conversation
- PUT /api/chat/conversation/:convoId/unblock - Unblock conversation
- DELETE /api/chat/conversation/:convoId/clear - Clear history

**Socket.io Events:**
- Client → Server: 'authenticate' (token) - Socket authentication
- Client → Server: 'send_message' ({receiver_id, content}, callback) - Send message
- Server → Client: 'receive_message' ({message, conversation}) - Receive message
- Client → Server: 'disconnect' - Connection cleanup

### Business Rules
1. All users can chat with any other user (no role restrictions)
2. One conversation per user pair (normalized pairing)
3. Messages persist in database regardless of delivery status
4. Clearing history only affects user who cleared (privacy)
5. Only blocker can unblock conversation
6. Blocked conversations prevent new messages
7. Socket authentication required for real-time features
8. Offline messages delivered as history on reconnection
