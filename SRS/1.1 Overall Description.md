# 1.1 Overall Description

## 1.1.0 Product Perspective

The Simple Workforce Manager (SWM) is a web-based, on-premise workforce management system built on the PERN stack (PostgreSQL, Express.js, React 19, Node.js 18+). The system provides a comprehensive digital solution for small and medium enterprises (SMEs) to manage their workforce operations through a single-tenant, self-hosted architecture that ensures complete data sovereignty and organizational control. 

The system leverages modern web technologies including Ant Design 5.28.0 for UI components, Socket.io 4.8.1 for real-time bidirectional communication, JWT (jsonwebtoken 9.0.2) for stateless authentication, and BCrypt 6.0.0 for secure password hashing. The architecture follows a client-server model with clear separation between presentation layer (React frontend), application layer (Express.js backend), and data layer (PostgreSQL database).

This system addresses the critical inefficiencies of manual workforce tracking through paper-based logs and error-prone Excel spreadsheets. By providing a centralized digital platform with three-tier role-based access control (Admin/Manager/Staff), real-time WebSocket-powered communication, and automated server-side data validation with parameterized queries, the system eliminates data inconsistencies, reduces administrative overhead, prevents SQL injection attacks, and preserves sensitive employee information within the organization's infrastructure through self-hosting deployment. 

The system SHALL support both local network deployment and mobile device access over LAN, enabling workforce management from any modern web browser without requiring native mobile applications. The system SHALL NOT require cloud infrastructure or third-party hosting services, ensuring complete data ownership by the deploying organization.

## 1.1.1 Product Functions

The system SHALL provide the following core functional modules:

- **Authentication & Authorization**: JWT-based stateless authentication with 1-hour token expiration, BCrypt password hashing with salt generation, three-tier role-based access control (Admin/Manager/Staff), mandatory password change enforcement on first login via `is_default_password` flag, password reset via email with crypto-generated tokens (15-minute expiration), and middleware-based route protection with role verification.

- **User Management**: Admin-exclusive CRUD operations for user accounts with unique constraints on username, email, and phone number; comprehensive profile management including employment metadata (job title, hire date, address, sex); database transaction support for atomic updates; and automatic profile creation with UPSERT operations to prevent orphaned records.

- **Task Management**: Complete workflow tracking system with ENUM-based status management (pending → in_progress → completed), bidirectional foreign key relationships tracking both assignee and assigner, due date management with TIMESTAMP precision, and manager-controlled task assignment with staff visibility and status update capabilities.

- **Attendance System**: Real-time clock-in/clock-out functionality with server-side CURRENT_TIMESTAMP to prevent client manipulation, attendance history with date-based indexing, automatic duration calculation between clock-in and clock-out times, and manager-level attendance monitoring across all staff members.

- **Real-Time Chat**: Socket.io-powered bidirectional WebSocket communication with JWT authentication on socket connection, 1-on-1 conversation support with normalized user pairing (user1_id < user2_id), conversation status management (active/blocked), per-user message history clearing with timestamp tracking (user1_cleared_at, user2_cleared_at), in-memory user-socket mapping for instant message delivery, and automatic conversation creation on first message.

- **Reports Module**: Structured submission system for staff work reports with title and content fields, timestamp-based submission tracking, manager-level visibility for all submitted reports, and foreign key cascade deletion to maintain referential integrity when users are removed.

- **Complaints System**: Ticket-style issue tracking with ENUM status workflow (open/resolved), threaded reply system via separate complaint_replies table, multi-user reply support allowing both staff and management responses, timestamp tracking for submission and replies, and admin/manager privileges for viewing and responding to all complaints.

- **Feedback Module**: Staff suggestion submission system with title and content fields, single-response model with reply text stored directly in feedback table, tracking of responder identity and response timestamp via replied_by and replied_at fields, and admin/manager capabilities for providing responses to staff feedback.

- **Allowances Management**: Financial tracking with DECIMAL(10,2) precision for monetary values, support for multiple frequency types (monthly, one-time, etc.) stored as VARCHAR, manager-controlled allowance creation and management, staff visibility of personal allowances, and comprehensive audit trail with creation timestamps.

- **Profile Management**: Self-service profile updates with transaction-based atomic operations, unique constraint enforcement on username, email, and phone number with specific error handling (409 Conflict), LEFT JOIN queries to handle users without profiles, support for extended employment details (job title, hire date, address, sex), and automatic avatar generation using first character of first name or username.

- **Settings Module**: Dual-layer configuration system with personal settings (date_format, notification_prefs as JSONB) and system-wide settings (company_name, currency_symbol) stored in key-value table, admin-exclusive access to system settings, UPSERT operations for settings updates, and automatic profile initialization for users without existing settings records.

## 1.1.2 User Characteristics

The system SHALL support three distinct user roles with varying levels of technical proficiency and operational responsibilities. Each role has specific access privileges and functional capabilities as defined below:

- **Admin**: High-privilege users with comprehensive system access including exclusive user management capabilities (create, edit, delete users), system-wide settings configuration (company name, currency symbol), and full visibility of complaints and feedback across the organization. Admins can view and manage all system data but delegate operational tasks (task assignment, attendance monitoring, allowance management) to managers. Admins are expected to have moderate technical proficiency for system administration tasks including database setup, environment configuration, and initial system deployment. The default admin account (username: "admin", password: "admin") is created via seedAdmin.js script and must be changed on first login.

- **Manager**: Operational supervisors with intermediate system privileges focused on workforce coordination activities including task creation and assignment to staff, attendance monitoring across all employees, report review and tracking, complaint and feedback response capabilities, and allowance creation and management. Managers have read-only access to staff profiles but cannot create or delete user accounts. Managers require basic technical proficiency with standard web applications and understanding of workforce management workflows.

- **Staff**: End-users with limited system privileges focused on daily operational activities including viewing and updating assigned tasks (status changes from pending → in_progress → completed), attendance clock-in/out with automatic timestamp recording, peer-to-peer communication via real-time chat, submission of work reports, complaints, and feedback, viewing personal allowances, and self-service profile updates. Staff members have no visibility into other users' data except for chat participants. Staff members require minimal technical proficiency with basic web navigation skills and modern browser usage.

## 1.1.3 Constraints

The system SHALL operate under the following technical, operational, and regulatory constraints:

- **Hardware Constraints**: The system SHALL run on standard server hardware with minimum specifications of 8GB RAM, dual-core processor (2.0 GHz or higher), and 50GB available storage. The system SHALL be capable of supporting 10-100 concurrent users in small to medium organizational deployments. The system SHALL be designed for single-server deployment and SHALL NOT support load balancing or horizontal scaling in the current version.

- **Network Constraints**: The system SHALL require stable Local Area Network (LAN) connectivity or static IP address configuration to ensure reliable WebSocket connections for real-time features. The backend server SHALL bind to 0.0.0.0 (all network interfaces) to enable mobile device access over LAN. The hosting environment SHALL permit inbound traffic on designated ports (default: TCP port 3000 for frontend, TCP port 5001 for backend). Network infrastructure SHALL NOT block WebSocket protocol upgrade requests (HTTP to WS). The system SHALL require minimum network bandwidth of 1 Mbps per concurrent user for optimal performance.

- **Technology Stack Constraints**: The system SHALL be strictly dependent on Node.js runtime environment (v18.0.0 or higher) for backend execution with CommonJS module system. The system SHALL require PostgreSQL relational database (v13.0 or higher) for data persistence with support for ENUM types, JSONB columns, and foreign key constraints. Client access SHALL require modern web browsers supporting ES6+ JavaScript, WebSocket protocol, and React 19 features. The system SHALL NOT be deployable on platforms lacking these specific technology versions or capabilities.

- **Security Constraints**: The system SHALL implement single-tenant architecture requiring data ownership and physical control by the deploying organization. The system SHALL NOT support multi-tenant cloud deployments to ensure compliance with data sovereignty requirements. CORS configuration SHALL explicitly whitelist frontend origin (default: http://localhost:3000). JWT secret SHALL be configured via environment variables and SHALL NOT be hardcoded or committed to version control. Database credentials SHALL be secured in environment configuration files with restricted file permissions. The system SHALL NOT implement HTTPS by default and SHALL require reverse proxy (nginx, Apache, or equivalent) for SSL/TLS termination in production environments. All database queries SHALL use parameterized statements to prevent SQL injection attacks.

- **Database Constraints**: The PostgreSQL database SHALL be initialized using the setupDatabase.js script to create required ENUM types (user_role, task_status, complaint_status, sex_type, conversation_status) and table schemas before application startup. Database connection pooling SHALL be managed via pg Pool with error event handlers. The system SHALL require a database user with CREATE, ALTER, INSERT, UPDATE, DELETE, and SELECT privileges. The database SHALL support transaction isolation levels for data consistency during concurrent operations.

- **Email Service Constraints**: Password reset functionality SHALL require SMTP server configuration via nodemailer with valid credentials stored in environment variables. Email delivery failures SHALL prevent password reset operations but SHALL NOT affect other system functionality. The system SHALL support standard SMTP protocols (SMTP, SMTPS, SMTP with STARTTLS).

## 1.1.4 Assumptions and Dependencies

The system's successful deployment and operation depend on the following assumptions and external dependencies:

- **Runtime Dependencies**: The system SHALL depend on the following runtime components:
  - **Backend Runtime**: Node.js 18.0.0 or higher with npm package manager, Express 5.1.0 (web framework), PostgreSQL driver (pg 8.16.3), Socket.io 4.8.1 (WebSocket server), jsonwebtoken 9.0.2 (JWT authentication), bcrypt 6.0.0 (password hashing), cors 2.8.5 (cross-origin resource sharing), dotenv 17.2.3 (environment configuration), nodemailer 7.0.10 (email service)
  - **Frontend Runtime**: React 19.2.0 (UI framework), React Router DOM 7.9.5 (client-side routing), Ant Design 5.28.0 (UI component library), Axios 1.13.1 (HTTP client), Socket.io-client 4.8.1 (WebSocket client), jwt-decode 4.0.0 (JWT parsing), moment 2.30.1 (date/time formatting)
  - **Database System**: PostgreSQL 13.0 or higher with support for ENUM types, JSONB columns, foreign key constraints, CASCADE operations, and READ COMMITTED transaction isolation level

- **Development Dependencies**: The development environment SHALL utilize nodemon 3.0.1 for backend development with automatic restart on file changes, react-scripts 5.0.1 for frontend build tooling and development server, and testing libraries (@testing-library/react 16.3.0, @testing-library/jest-dom 6.9.1, @testing-library/user-event 13.5.0) for component and integration testing

- **Environment Configuration Requirements**: The system SHALL require the following environment variables:
  - **Backend Configuration (.env)**: PORT (default: 5001), DB_USER (PostgreSQL username), DB_HOST (database host address), DB_DATABASE (database name), DB_PASSWORD (database password), DB_PORT (default: 5432), JWT_SECRET (cryptographically secure random string, minimum 32 characters), CORS_ORIGIN (frontend URL for CORS whitelist), FRONTEND_URL (base URL for email links), SMTP configuration (host, port, username, password, secure flag)
  - **Frontend Configuration (.env)**: REACT_APP_API_URL (backend API endpoint, format: http://[host]:[port]/api)

- **Browser Requirements**: Users SHALL access the system through modern web browsers meeting the following minimum versions: Chrome 90+, Microsoft Edge 90+, Firefox 88+, Safari 14+. Browsers SHALL have JavaScript enabled, WebSocket protocol support (RFC 6455), LocalStorage API for JWT token persistence (minimum 5MB quota), and CSS Grid/Flexbox support for Ant Design component rendering. Mobile browsers (iOS Safari 14+, Chrome Mobile 90+) SHALL be supported for responsive access over LAN with touch-optimized interfaces.

- **Network Infrastructure Requirements**: The hosting environment SHALL permit inbound TCP traffic on port 3000 (Frontend React application served via react-scripts development server or static file server) and port 5001 (Backend Express API with Socket.io WebSocket server). Firewall configurations SHALL allow WebSocket protocol upgrade requests (HTTP → WS protocol switch per RFC 6455) for real-time communication features. For mobile device access, the server SHALL be accessible via LAN IP address (IPv4 private address ranges: 192.168.0.0/16, 172.16.0.0/12, 10.0.0.0/8) with network-wide binding (0.0.0.0). The system SHALL NOT require public internet connectivity for core functionality.

- **Deployment Requirements and Procedures**: 
  - The database SHALL be initialized via `node setupDatabase.js` script before first application run to create schema and ENUM types
  - The default admin account SHALL be seeded via `node seedAdmin.js` script with credentials (username: "admin", password: "admin")
  - Backend and frontend SHALL run as separate processes: Backend via `node index.js` (production) or `npm run dev` (development), Frontend via `npm start` (development) or static file serving (production)
  - For production deployment, frontend SHALL be built via `npm run build` command and served via static file server (nginx, Apache) or reverse proxy
  - The system SHALL be deployed on trusted internal networks; external internet exposure SHALL require additional security hardening measures including HTTPS/TLS encryption, rate limiting, intrusion detection systems, and regular security audits

- **Operational Requirements and Assumptions**:
  - System administrators SHALL perform regular database backups using PostgreSQL pg_dump utility or equivalent backup solutions with minimum daily backup frequency recommended
  - System logs SHALL be monitored for authentication failures, database connection errors, and application exceptions
  - User accounts SHALL be managed exclusively through the admin web interface; direct database manipulation SHALL NOT be supported and may cause data inconsistencies
  - Password reset functionality SHALL assume successful email delivery (requires valid SMTP configuration and network connectivity to mail server)
  - WebSocket connections SHALL be maintained during active chat sessions; client disconnections SHALL trigger automatic reconnection attempts via Socket.io client with exponential backoff strategy
  - The system SHALL assume continuous availability of PostgreSQL database service; database downtime SHALL result in complete system unavailability
  - System administrators SHALL have moderate technical proficiency including command-line interface usage, environment variable configuration, and basic troubleshooting capabilities
