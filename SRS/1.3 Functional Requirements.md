# 1.3. Functional Requirements

This section defines the functional requirements for the Simple Workforce Manager system using the Input/Processing/Output format. Each requirement specifies user actions (Input), system logic (Processing), and system responses (Output) for all 11 core functional modules.

## 1.3.1. Authentication & Authorization

### 1.3.1.1. User Login

**Description:** Users authenticate with username and password credentials to access the system.

**Input:**
- Username (string, required)
- Password (string, required)
- Login form submission via POST /api/auth/login

**Processing:**
1. System validates that both username and password fields are provided
2. System queries users table for matching username
3. System compares provided password with stored BCrypt password hash using bcrypt.compare()
4. If credentials are valid, system generates JWT payload containing user ID, role, and is_default_password flag
5. System signs JWT token with JWT_SECRET and 1-hour expiration using jsonwebtoken library
6. System returns authentication token to client

**Output:**
- Success (200): JSON response with JWT token and success message
- Failure (400): "Username and password are required" if fields missing
- Failure (401): "Invalid credentials" if username not found or password mismatch
- Failure (500): "Server error during login" for unexpected errors
- Client stores JWT token in browser LocalStorage
- Client redirects to dashboard or password reset page based on is_default_password flag

### 1.3.1.2. Mandatory Password Reset (First Login)

**Description:** Users with default passwords must change their password before accessing the system.

**Input:**
- New password (string, minimum 6 characters)
- JWT token from authenticated session
- Form submission via POST /api/auth/reset-password

**Processing:**
1. System authenticates request using JWT token from Authorization header
2. System validates new password meets minimum length requirement (MIN_PASSWORD_LENGTH constant)
3. System generates salt using bcrypt.genSalt(10)
4. System hashes new password with generated salt using bcrypt.hash()
5. System updates users table: sets password_hash to new hash, sets is_default_password to false
6. System commits database transaction

**Output:**
- Success (200): "Password reset successful. Please log in again."
- Failure (400): "Password must be at least 6 characters long" if validation fails
- Failure (401): "No token, authorization denied" if JWT missing
- Failure (500): "Server error" for database errors
- Client clears authentication token and redirects to login page


### 1.3.1.3. Forgot Password Request

**Description:** Users can request a password reset link via email when they forget their password.

**Input:**
- Email address (string, required)
- Form submission via POST /api/auth/forgot-password

**Processing:**
1. System queries users table for account matching provided email address
2. If user exists, system generates cryptographically secure random token using crypto.randomBytes(32).toString('hex')
3. System calculates token expiration timestamp (current time + PASSWORD_RESET_EXPIRY_MINUTES)
4. System updates users table: stores password_reset_token and password_reset_expires
5. System constructs reset URL: ${FRONTEND_URL}/reset-password/${token}
6. System sends HTML email via nodemailer with reset link and expiration notice
7. System returns generic success message regardless of email existence (security best practice)

**Output:**
- Success (200): "If an account with that email exists, a reset link has been sent."
- Failure (500): "Server error" for email delivery failures
- Email sent to user with password reset link (15-minute expiration)
- Preview URL logged to console for Ethereal test accounts

### 1.3.1.4. Password Reset Confirmation

**Description:** Users complete password reset using the token received via email.

**Input:**
- Reset token (string from URL parameter)
- New password (string, required)
- Form submission via POST /api/auth/perform-reset

**Processing:**
1. System validates that both token and new password are provided
2. System queries users table for matching password_reset_token where password_reset_expires > NOW()
3. If valid token found, system generates salt using bcrypt.genSalt(10)
4. System hashes new password with generated salt
5. System updates users table: sets password_hash, clears password_reset_token and password_reset_expires, sets is_default_password to false
6. System commits database transaction

**Output:**
- Success (200): "Password reset successful. You can now log in."
- Failure (400): "Token and new password are required" if fields missing
- Failure (400): "Password reset token is invalid or has expired" if token not found or expired
- Failure (500): "Server error" for database errors
- Client redirects to login page with success notification

### 1.3.1.5. JWT Token Validation

**Description:** System validates JWT tokens for protected API endpoints.

**Input:**
- Authorization header with Bearer token format: "Bearer <jwt_token>"
- HTTP request to protected endpoint

**Processing:**
1. Middleware extracts Authorization header from request
2. System splits header to extract token after "Bearer " prefix
3. System verifies token signature using jwt.verify() with JWT_SECRET
4. System decodes token payload to extract user object (id, role)
5. System attaches decoded user object to request object (req.user)
6. System passes control to next middleware or route handler

**Output:**
- Success: Request proceeds to route handler with req.user populated
- Failure (401): "No token, authorization denied" if Authorization header missing
- Failure (401): "Token is malformed, authorization denied" if Bearer format incorrect
- Failure (401): "Token is not valid" if signature verification fails or token expired


### 1.3.1.6. Role-Based Access Control

**Description:** System enforces role-based permissions for protected endpoints.

**Input:**
- Authenticated user with role (admin, manager, or staff)
- HTTP request to role-protected endpoint
- Allowed roles configuration for endpoint

**Processing:**
1. Middleware receives req.user from JWT authentication
2. System extracts user role from req.user.role
3. System compares user role against allowed roles array for endpoint
4. If role matches, system passes control to route handler
5. If role does not match, system returns 403 Forbidden error

**Output:**
- Success: Request proceeds to route handler
- Failure (403): "Forbidden: Required role(s): [role1, role2]" with specific roles listed
- HTTP 403 status code prevents unauthorized access

## 1.3.2. User Management

### 1.3.2.1. Create User Account

**Description:** Admin creates new user accounts with profile information.

**Input:**
- Username (string, required, unique)
- Email (string, required, unique)
- Password (string, required)
- Role (enum: admin, manager, staff, required)
- First name (string, required)
- Last name (string, required)
- Phone number (string, required, unique)
- Sex (enum: male, female, other, required)
- Job title (string, optional)
- Form submission via POST /api/staff/ (admin only)

**Processing:**
1. System validates all required fields are provided
2. System initiates database transaction using client.query("BEGIN")
3. System generates BCrypt salt using bcrypt.genSalt(10)
4. System hashes password with salt using bcrypt.hash()
5. System inserts record into users table with username, email, password_hash, role, and is_default_password=true
6. System retrieves newly created user_id from INSERT RETURNING clause
7. System inserts record into user_profiles table with user_id, first_name, last_name, phone_number, sex, and job_title
8. System commits transaction using client.query("COMMIT")
9. If any error occurs, system rolls back transaction using client.query("ROLLBACK")

**Output:**
- Success (201): "User created successfully"
- Failure (400): "All fields are required" if validation fails
- Failure (409): "Failed to create user. [constraint detail]" for duplicate username, email, or phone number
- Failure (500): "Server error creating user" for database errors
- Database transaction ensures atomic operation (both user and profile created or neither)

### 1.3.2.2. View All Users

**Description:** Admin and Manager view list of all non-admin users with profile information.

**Input:**
- Authenticated user with admin or manager role
- HTTP GET request to /api/staff/

**Processing:**
1. System authenticates request and verifies user has admin or manager role
2. System executes LEFT JOIN query between users and user_profiles tables
3. System filters results to exclude users with role='admin'
4. System retrieves user_id, username, email, role, first_name, last_name, phone_number, sex, and job_title
5. System returns array of user objects

**Output:**
- Success (200): JSON array of user objects with profile information
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): admin, manager" if insufficient permissions
- Failure (500): "Server error" for database errors


### 1.3.2.3. View Single User Details

**Description:** Admin and Manager view detailed information for a specific user.

**Input:**
- User ID (integer, URL parameter)
- Authenticated user with admin or manager role
- HTTP GET request to /api/staff/:id

**Processing:**
1. System authenticates request and verifies user has admin or manager role
2. System executes LEFT JOIN query between users and user_profiles tables for specified user_id
3. System filters to exclude admin users
4. System retrieves comprehensive user data including hire_date and address
5. System returns single user object or 404 if not found

**Output:**
- Success (200): JSON object with complete user and profile information
- Failure (404): "Staff user not found" if user_id doesn't exist or is admin
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): admin, manager" if insufficient permissions
- Failure (500): "Server error" for database errors

### 1.3.2.4. Update User Account

**Description:** Admin updates existing user account and profile information.

**Input:**
- User ID (integer, URL parameter)
- Username (string, required, unique)
- Email (string, required, unique)
- Role (enum: admin, manager, staff, required)
- First name (string, required)
- Last name (string, required)
- Phone number (string, required, unique)
- Sex (enum: male, female, other, required)
- Job title (string, optional)
- Form submission via PUT /api/staff/:id (admin only)

**Processing:**
1. System validates all required fields are provided
2. System initiates database transaction using client.query("BEGIN")
3. System updates users table with username, email, and role for specified user_id (excluding admin users)
4. System performs UPSERT on user_profiles table using INSERT ... ON CONFLICT (user_id) DO UPDATE
5. System updates first_name, last_name, phone_number, sex, and job_title
6. System commits transaction using client.query("COMMIT")
7. If any error occurs, system rolls back transaction

**Output:**
- Success (200): "User updated successfully"
- Failure (400): "All required fields must be provided" if validation fails
- Failure (409): "Failed to update user. [constraint detail]" for duplicate username, email, or phone number
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): admin" if insufficient permissions
- Failure (500): "Server error" for database errors

### 1.3.2.5. Delete User Account

**Description:** Admin deletes user account and all associated data.

**Input:**
- User ID (integer, URL parameter)
- Authenticated admin user
- HTTP DELETE request to /api/staff/:id

**Processing:**
1. System authenticates request and verifies user has admin role
2. System executes DELETE query on users table for specified user_id
3. System filters to prevent deletion of admin users (role != 'admin')
4. Database CASCADE constraints automatically delete related records in user_profiles, tasks, attendance, reports, complaints, feedback, allowances, messages, and conversations tables
5. System retrieves deleted username from RETURNING clause

**Output:**
- Success (200): "User [username] deleted successfully"
- Failure (404): "Staff user not found or is an admin" if user_id doesn't exist or is admin
- Failure (409): "Cannot delete user. They are referenced in other records." if foreign key constraint prevents deletion
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): admin" if insufficient permissions
- Failure (500): "Server error" for database errors


## 1.3.3. Task Management

### 1.3.3.1. Create Task Assignment

**Description:** Admin or Manager creates and assigns tasks to staff members.

**Input:**
- Title (string, required)
- Description (string, optional)
- Assigned to user ID (integer, required)
- Due date (timestamp, optional)
- Authenticated user with admin or manager role
- Form submission via POST /api/tasks/

**Processing:**
1. System validates title and assigned_to fields are provided
2. System retrieves assigned_by user ID from JWT token (req.user.id)
3. System verifies assigned_to user exists by querying users table
4. System inserts new record into tasks table with title, description, assigned_to, assigned_by, due_date, and default status='pending'
5. System records created_at timestamp automatically via database DEFAULT CURRENT_TIMESTAMP
6. System returns newly created task object with task_id

**Output:**
- Success (201): JSON object with complete task details including task_id
- Failure (400): "Title and assigned_to are required" if validation fails
- Failure (404): "Assigned user does not exist" if assigned_to user_id not found
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): admin, manager" if insufficient permissions
- Failure (500): "Server error" for database errors

### 1.3.3.2. View My Assigned Tasks (Staff)

**Description:** Staff members view tasks assigned to them.

**Input:**
- Authenticated staff user
- HTTP GET request to /api/tasks/mytasks

**Processing:**
1. System authenticates request and extracts user ID from JWT token
2. System executes query with LEFT JOIN between tasks and users tables
3. System filters tasks where assigned_to matches authenticated user ID
4. System retrieves task details along with assigned_by_username
5. System orders results by created_at DESC (newest first)

**Output:**
- Success (200): JSON array of task objects with assigner username
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (500): "Server error" for database errors
- Empty array if no tasks assigned to user

### 1.3.3.3. View All Tasks (Manager)

**Description:** Admin or Manager views all tasks in the system.

4. System orders results by created_at DESC (newest first)

**Output:**
- Success (200): JSON array of all task objects with assignee and assigner usernames
- Failure (401): "No token, authorization denied" if not authenticated

## 1.3.4. Attendance System

### 1.3.4.1. Clock In

**Description:** Staff members clock in to record start of work shift.

**Input:**
- Authenticated staff user
- Clock-in button click via POST /api/attendance/clock-in

**Processing:**
1. System authenticates request and verifies user has staff role
2. System retrieves user ID from JWT token
3. System queries attendance table for existing clock-in record where user_id matches, attendance_date = CURRENT_DATE, and clock_out_time IS NULL
4. If active clock-in exists, system returns 409 Conflict error
5. If no active clock-in, system inserts new record into attendance table with user_id
6. Database automatically sets attendance_date = CURRENT_DATE and clock_in_time = CURRENT_TIMESTAMP
7. System returns newly created attendance record

**Output:**
- Success (201): "Clocked in successfully" with attendance record including attendance_id, user_id, attendance_date, and clock_in_time
- Failure (409): "You are already clocked in" if active session exists
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): staff" if insufficient permissions
- Failure (500): "Server error" for database errors

### 1.3.4.2. Clock Out

**Description:** Staff members clock out to record end of work shift.

**Input:**
- Authenticated staff user
- Clock-out button click via POST /api/attendance/clock-out

**Processing:**
1. System authenticates request and verifies user has staff role
2. System retrieves user ID from JWT token
3. System queries attendance table for active clock-in record where user_id matches, attendance_date = CURRENT_DATE, and clock_out_time IS NULL
4. If no active clock-in found, system returns 400 Bad Request error
5. If active clock-in exists, system retrieves attendance_id
6. System updates attendance record: sets clock_out_time = CURRENT_TIMESTAMP
7. System returns updated attendance record with RETURNING clause

**Output:**
- Success (200): "Clocked out successfully" with attendance record including clock_out_time
- Failure (400): "You are not clocked in" if no active session exists
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (403): "Forbidden: Required role(s): staff" if insufficient permissions
- Failure (500): "Server error" for database errors


### 1.3.4.3. Check Clock-In Status

**Description:** Staff members check their current clock-in status.

**Input:**
- Authenticated staff user
- HTTP GET request to /api/attendance/status

**Processing:**
1. System authenticates request and verifies user has staff role
2. System retrieves user ID from JWT token
3. System queries attendance table for active clock-in record where user_id matches, attendance_date = CURRENT_DATE, and clock_out_time IS NULL
4. If active record found, system returns isClockedIn: true with record details
5. If no active record, system returns isClockedIn: false

**Output:**

- Failure (401): "No token, authorization denied" if not authenticated

- Failure (500): "Server error" for database errors

## 1.3.5. Real-Time Chat

### 1.3.5.1. Search Users for Chat

**Description:** Users search for other users to initiate conversations.

**Input:**
- Search query string (partial username or email)
- Authenticated user
- HTTP GET request to /api/chat/search?query=<search_term>

**Processing:**
1. System authenticates request and retrieves current user ID
2. System executes LEFT JOIN query between users and user_profiles tables
3. System filters using ILIKE for case-insensitive partial matching on username or email
4. System excludes current user from results (user_id != authenticated user ID)
5. System returns matching users with user_id, username, email, first_name, and last_name

**Output:**
- Success (200): JSON array of matching user objects
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (500): "Server Error" for database errors
- Empty array if no matches found

### 1.3.5.2. View Conversation List

**Description:** Users view list of all their active conversations.

**Input:**
- Authenticated user
- HTTP GET request to /api/chat/conversations

**Processing:**
1. System authenticates request and retrieves current user ID
2. System queries conversations table where user1_id OR user2_id matches authenticated user
3. System performs JOIN with users table to retrieve other participant details
4. System uses CASE statement to determine other participant: if user1_id matches current user, return user2_id, else return user1_id
5. System performs LEFT JOIN with user_profiles to retrieve first_name and last_name
6. System returns conversation_id, status, blocked_by, and other participant details

**Output:**
- Success (200): JSON array of conversation objects with participant information
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (500): "Server Error" for database errors
- Empty array if no conversations exist


### 1.3.5.3. View Message History

**Description:** Users view message history with a specific conversation partner.

**Input:**
- Other user ID (integer, URL parameter)
- Authenticated user
- HTTP GET request to /api/chat/history/:userId

**Processing:**
1. System authenticates request and retrieves current user ID
2. System normalizes conversation pairing: user1_id = MIN(current_user_id, other_user_id), user2_id = MAX(current_user_id, other_user_id)
3. System queries conversations table for matching user1_id and user2_id
4. If no conversation exists, system returns empty response with conversation: null, messages: []
5. If conversation exists and status='blocked', system returns 403 Forbidden error
6. System determines which cleared_at timestamp to use based on current user position (user1_cleared_at or user2_cleared_at)
7. System queries messages table for conversation_id where sent_at > cleared_at timestamp
8. System orders messages by sent_at ASC (chronological order)
9. System returns both conversation object and messages array

**Output:**
- Success (200): JSON object with conversation details and messages array
- Failure (403): "This conversation is blocked." if conversation status is blocked
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (500): "Server Error" for database errors
- Empty messages array if no messages or all messages cleared

### 1.3.5.4. Send Message (WebSocket)

**Description:** Users send real-time messages via WebSocket connection.

**Input:**
- Receiver user ID (integer)
- Message content (string)
- Socket.io event: 'send_message' with data object {receiver_id, content}
- Callback function for acknowledgment

**Processing:**
1. System retrieves sender_id from in-memory userSocketMap using socket.id
2. If sender not authenticated, system returns error via callback
3. System normalizes conversation pairing: user1_id = MIN(sender_id, receiver_id), user2_id = MAX(sender_id, receiver_id)
4. System queries conversations table for existing conversation
5. If no conversation exists, system creates new conversation with status='active'
6. If conversation exists and status='blocked', system returns error via callback
7. System inserts new message into messages table with conversation_id, sender_id, content
8. Database automatically sets sent_at = CURRENT_TIMESTAMP
9. System retrieves receiver socket ID from userSocketMap
10. If receiver online, system emits 'receive_message' event to receiver socket with message and conversation data
11. System returns success acknowledgment via callback with message and conversation objects

**Output:**
- Success: Callback receives {status: 'ok', message: {...}, conversation: {...}}
- Real-time: Receiver receives 'receive_message' event with message payload
- Failure: Callback receives {status: 'error', message: 'Not authenticated'} if not authenticated
- Failure: Callback receives {status: 'error', message: 'This conversation is blocked.'} if blocked
- Failure: Callback receives {status: 'error', message: 'Server error'} for database errors
- Message persisted in database regardless of receiver online status

### 1.3.5.5. Socket Authentication

**Description:** Users authenticate their WebSocket connection with JWT token.

**Input:**
- JWT token string
- Socket.io event: 'authenticate' with token payload

**Processing:**
1. System receives authenticate event from client socket
2. System verifies JWT token using jwt.verify() with JWT_SECRET
3. System extracts user object from decoded token payload
4. System stores mapping in userSocketMap: user_id → socket_id
5. System logs successful authentication with user ID and socket ID
6. If verification fails, system logs error and disconnects socket

**Output:**
- Success: User-socket mapping stored, connection maintained
- Failure: Socket disconnected if JWT verification fails
- Console log: "User [user_id] authenticated with socket [socket_id]" on success
- Console log: "Socket authentication failed: [error]" on failure

### 1.3.5.6. Block Conversation

**Description:** Users block a conversation to prevent further messages.

**Input:**
- Conversation ID (integer, URL parameter)
- Authenticated user
- HTTP PUT request to /api/chat/conversation/:convoId/block

**Processing:**
1. System authenticates request and retrieves current user ID
2. System updates conversations table: sets status='blocked', blocked_by=current_user_id
3. System filters update to only conversations where user1_id OR user2_id matches current user
4. System returns updated conversation object with RETURNING clause
5. If no rows updated, system returns 404 error

**Output:**
- Success (200): JSON object with updated conversation (status='blocked', blocked_by set)
- Failure (404): "Conversation not found" if conversation_id doesn't exist or user not participant
- Failure (401): "No token, authorization denied" if not authenticated
- Failure (500): "Server Error" for database errors


### 1.3.5.7. Unblock Conversation

**Description:** Users unblock a conversation they previously blocked.

**Input:**
- Conversation ID (integer, URL parameter)
- Authenticated user
- HTTP PUT request to /api/chat/conversation/:convoId/unblock

**Processing:**
1. System authenticates request and retrieves current user ID
2. System updates conversations table: sets status='active', blocked_by=NULL
3. System filters update to only conversations where conversation_id matches AND blocked_by matches current user ID
4. System returns updated conversation object with RETURNING clause
5. If no rows updated, system returns 403 error (user didn't block conversation or not participant)

**Output:**
- Success (200): JSON object with updated conversation (status='active', blocked_by=NULL)

**Description:** System automatically maintains referential integrity through cascade operations.

**Input:**

2. When user deleted, system automatically deletes related records in:

### 1.3.12.10. Connection Pool Management

**Description:** System manages database connection pooling for optimal performance.

**Input:**
- Database query operations from any module
- Application startup and shutdown

**Processing:**
1. System creates PostgreSQL connection pool using pg.Pool with configuration:
   - user: DB_USER environment variable
   - host: DB_HOST environment variable
   - database: DB_DATABASE environment variable
   - password: DB_PASSWORD environment variable
   - port: DB_PORT environment variable (default: 5432)
2. Pool maintains reusable database connections
3. System registers error event handler for unexpected connection errors
4. For simple queries, system uses db.query(text, params) wrapper
5. For transactions, system acquires dedicated client using db.pool.connect()
6. System releases clients back to pool after use
7. On application shutdown, system closes all connections using db.pool.end()

**Output:**
- Success: Efficient connection reuse across all database operations
- Success: Automatic connection management without manual open/close
- Console log: "Unexpected database error: [error]" for connection issues
- Improved performance through connection pooling
- Graceful connection cleanup on application termination

### 1.3.12.11. Environment Configuration Management

**Description:** System loads configuration from environment variables for deployment flexibility.

**Input:**
- .env file in backend directory

   - PORT: Backend server port (default: 5001)

   - JWT_SECRET: Secret key for JWT signing
   - CORS_ORIGIN: Allowed frontend origin for CORS
   - FRONTEND_URL: Base URL for email links
3. Frontend reads REACT_APP_API_URL from environment at build time
4. System uses environment variables throughout application with fallback defaults
5. Sensitive values (JWT_SECRET, DB_PASSWORD) never hardcoded in source code

**Output:**
- Success: Application configured from environment variables
- Success: Different configurations for development, staging, production
- Failure: Application fails to start if critical variables missing
- Security: Sensitive credentials isolated from source code
- Flexibility: Easy deployment across different environments without code changes
